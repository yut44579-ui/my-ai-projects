TASK-004A 前端施工方案评审
最终判定：暂缓交 Claude CLI，必须先补齐施工契约

这版的方向是对的，而且已经明确拒绝 Demo，提出了真实 Excel、真实 API、真实报表下载和浏览器验证。

但目前仍有一个核心问题：

方案证明了“部分按钮必须调用真实 API”，却还没有完整定义“一个用户可以实际完成报表业务”的前端闭环。

尤其是目标中明确包含「建任务 → 看到 Spec → 执行 → 下载 → 执行记录」，但验收标准没有覆盖完整链路。

建议先做一轮小幅修订，不需要推翻技术选型。

一、必须先改的阻塞项
BLOCKER-1：目标链路与 Acceptance Criteria 不完整

目标是：

上传真实 Excel
    ↓
建任务
    ↓
看到 Report Spec
    ↓
执行
    ↓
下载真实 Excel
    ↓
查看执行记录

但当前 AC 只明确验证：

环节	当前验收
上传文件	✅ AC-02
建任务	❌ 未单独验收
查看 Report Spec	❌ 未验收
执行报表	⚠️ AC-03 只提到 /api/execute
下载 Excel	✅ AC-04
执行记录	❌ 未验收

必须补齐建任务、Spec 展示、执行记录的真实行为和验收证据。

否则 Claude 可能做出这样的页面：

┌──────────────────────────────┐
│ 数据                         │
│ [上传文件]                   │
│                              │
│ 建任务                       │
│ [生成报表]                   │
│                              │

│ [一些展示文字]               │
│                              │
│ 执行结果                     │
│ [下载]                       │
│                              │
│ 执行记录                     │
│ 暂无记录                     │
└──────────────────────────────┘

页面看起来完整，但「建任务」「Spec」「执行记录」可能只是静态展示。

建议补充

明确每个区块的真实职责：

① 数据：
   选择并上传真实 Excel；
   显示后端返回的文件标识、文件名、行数和上传状态。

② 建任务：
   使用真实后端接口创建任务；
   显示任务 ID 和创建结果；
   任务创建失败必须显示错误。

③ Report Spec：
   展示后端返回的真实 Spec；
   不允许在前端硬编码完整业务 Spec 冒充接口结果。

④ 执行结果：
   使用真实任务 ID 调用执行接口；
   显示真实执行状态、金额、结果文件标识；
   成功后才能启用下载。

⑤ 执行记录：
   从真实后端获取执行记录；
   显示至少任务 ID、状态、创建时间、金额或结果信息；
   刷新后仍能读取已有记录。

字段和接口名称必须以 002C 的实际 API 契约为准，不能让 Claude 自己猜。

BLOCKER-2：没有提供 002C API 的真实接口契约

方案要求：

JavaScript
fetch('/api/upload', FormData)
GET /api/download/{execution_id}

但没有明确：

/api/upload 的完整请求与响应格式；

创建任务的接口是什么；

Report Spec 从哪里获取；

/api/execute 需要哪些参数；

execution_id 如何产生；

执行记录接口是什么；

失败响应格式；

上传后的文件如何与任务关联；

下载接口是否需要任务 ID、执行 ID 或其他参数。

这对原生 JS 尤其重要，因为没有 Vue/React 类型系统或 API SDK 帮助发现错误。

必须补充的内容

在施工指令中加入：

【前置 API 契约】
Claude 必须先阅读并核对 002C 已实现的 API 路由、请求参数、
响应 JSON、错误响应、任务 ID、执行 ID、下载接口和执行记录接口。

以实际后端代码及已通过的 API 测试为准。
不得自行猜测接口名称、字段或业务流程。
若前端目标功能所需的 API 在 002C 中不存在，必须报告 BLOCKED，
不得修改后端补接口。

如果 002C 尚未提供创建任务、获取 Spec、执行记录等接口，那么当前 TASK 不能声称实现完整目标。

BLOCKER-3：缺少“非 Demo”的可操作业务验收

当前 AC-02～04 主要验证：

上传成功；

调用执行接口；

下载文件。

但这仍然可能由一个非常简单的页面完成，甚至不需要真正的任务状态管理。

要证明它不是 Demo，必须验证：

用户能够在页面上完成一次真实业务操作，并且后续操作依赖前一步真实返回的数据。

建议增加一个端到端验收：

AC-09 【真实业务闭环】
使用浏览器完成以下操作，不通过 curl 代替页面操作：

1. 选择真实 data/Online Retail.xlsx；
2. 上传并显示后端返回的文件信息；
3. 创建真实任务；
4. 显示后端返回的任务 ID 和 Report Spec；
5. 点击执行；
6. 显示真实执行结果；
7. 点击下载；
8. 使用 openpyxl 读取下载文件并验证内容；
9. 刷新页面；
10. 从真实后端读取并显示该任务的执行记录。

每一步必须使用前一步真实返回的数据。
任一步失败均不得伪装成成功。

这条才是对「不是 demo index」最直接的验收。

二、强烈建议补强的地方
1. AC-03 的“真实金额一致”需要明确比较方式

目前：

页面显示真实金额，与直接 curl 同一个 API 的值一致。

问题在于：

页面是否真的调用了接口？

页面金额来自哪个响应字段？

curl 是否使用相同任务、相同文件和相同参数？

金额是字符串还是浮点数？

是否允许浮点显示格式差异？

建议改成：

浏览器执行与独立 curl 执行必须使用相同的真实输入文件、
相同的任务配置和相同的计算口径。

页面显示金额必须来自浏览器实际收到的 API 响应，
不得从前端常量或预设结果读取。

测试比较原始数值，允许页面仅改变显示格式。
2. AC-05 的失败测试不够完整

目前只要求上传 .txt。

这能验证错误展示，但不能证明：

后端返回 4xx 时能正确显示；

网络请求失败时页面不会卡死；

执行失败时不会出现“成功”；

下载失败时不会误显示下载完成。

建议至少增加：

- 上传接口返回错误时，页面显示可读错误；
- 执行接口失败时，页面显示失败状态；
- 下载失败时，不得显示成功下载；
- 请求进行中时，相关按钮应禁用或防止重复提交。

不一定全部写成独立 AC，但应纳入施工要求和测试证据。

3. AC-07 的关键词扫描不适合作为唯一反 Demo 证据
Bash
grep -rn "mock\|fake\|TODO\|hardcode\|setTimeout" web/

它可以作为辅助检查，但不能证明没有 Demo。

例如：

没有 mock 字样，也可以写死假数据；

真实功能可能需要合法的 setTimeout；

hardcode 可能出现在注释或无关文本中；

Windows 环境未必有 grep。

建议改为：

AC-07：
代码检查不得发现假 API、假数据、假下载、静态伪造业务结果。
同时检查所有业务按钮的事件处理和 API 调用链。

关键词扫描仅作为辅助证据，不作为唯一判定依据。

如果坚持使用命令，建议明确要求在项目实际环境中执行可用的等价命令。

4. 五区块需要明确是否是独立功能区，而不是五个静态标题

“单页五区块”本身没有问题，但应明确：

每个区块有真实数据来源；

每个区块有实际交互；

区块之间存在真实状态传递；

无数据时显示空状态；

当前任务未创建时，执行按钮不可用；

未产生执行结果时，下载按钮不可用。

否则可能出现“五个标题 + 两个真正工作的按钮”。

三、Scope 有一个潜在风险

当前允许修改：

app/api.py

只加静态文件挂载。

这条边界是合理的，但建议补一句：

若 002C 的现有路由与静态挂载发生冲突，
不得修改既有 API 逻辑；
必须报告 BLOCKED 或提出最小范围修复建议。

另外，静态挂载应确保不会覆盖既有 /api/* 路由。具体实现需要以 FastAPI 当前路由注册顺序和已有结构为准。

四、当前方案哪些地方已经做得很好？
1. 明确拒绝 Demo

这部分方向正确：

禁止 mock 数据
禁止假 API
禁止假下载
禁止 setTimeout 假装成功
禁止硬编码结果

这是必要条件，但还不是充分条件。

2. 要求真实 Excel
data/Online Retail.xlsx

而不是造一个几行的测试文件，这一点很重要。

3. 要求真实下载后用 openpyxl 读取

这能排除很多“下载按钮只是生成一个空文件”的伪实现。

index.html

符合最小垂直切片和轻量优先的目标。

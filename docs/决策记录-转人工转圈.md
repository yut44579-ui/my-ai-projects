# 转人工的「转圈」：人工接管才停

> 用户的原话：
> 「你转人工的时候，只有在人工点了接管以后，才会出现已经转人工，
>   否则会一直打转的状态，顺时针转的那种符号吧，
>   然后人工接管之后才会停止转。」

---

## D93 ★★★ 「已转人工」是一句话，「在等人接」是一个状态

**原来的做法**：转人工时发一句 `—— 已转人工，稍等 ——`。

**★ 为什么这句话不够**：
```
用户看到"已转人工，稍等"之后会想：
  · 转了吗？
  · 有人吗？
  · 要等多久？
  · 还是说系统把我忘了？
→ 他没法判断到底有没有人在
→ 等两分钟没动静，他就走了
```

**★★ 转圈不一样：它是一个不用思考就能懂的状态指示。**
```
转着 = 还在等
停了 = 有人了
```
用户不需要理解任何文字，瞟一眼就知道。

### 三种状态的完整表达

| 时刻 | 客户端显示 | 顶栏 |
|---|---|---|
| AI 转人工 | 🟠 转圈的等待条「正在为你转接人工客服…」<br>副标题「有人接手后会立刻通知你」 | 等待人工接入… |
| 人工点「接管」 | ⬜ 转圈消失，换成绿色 **「客服已接入」** | 客服已接入 |
| 人工发第一句 | ✅ 转圈确保已停，出现真人回复 | 客服在线 |

**实测（走公网）**：
```
① 转人工之后   转圈中 ✅ | 等待条有 | 已接入：还没出现 | 顶栏：等待人工接入…
② 人工接管     转圈中 ✅ 停了 | 已接入 ✅「客服已接入」 | 顶栏：客服已接入
③ 人工回复     转圈中 ✅ 停了 | 最后一条：报价要工程师看过图纸才能定… | 顶栏：客服在线
```

## D94 技术实现：用一条新的消息类型表示"停转"

**数据层**：`web_outbox.kind` 从 2 种扩到 4 种：

```
system  一般的系统提示（灰色小字）
waiting ★ 转圈的等待指示 —— 客户端看到就转
taken   ★ 停转 —— 客户端看到就停，换成"客服已接入"
human   真人说的话
```

**★ 为什么用"再发一条 taken"来表示停转，而不是删掉那条 waiting**：
```
① 客户端是按 seq 拉增量的 —— 删掉的话它根本不知道
② "等过"这个事实本身也应该留在记录里（事后查"用户等了多久"要靠它）
```

**★ 触发的两处**（缺一不可）：
```
/api/handover/{id}/take   → stop_waiting  （点了接管）
/api/handover/{id}/reply  → 消息本身 kind=human，客户端也会停
```
两处都做，是因为**客服可能不点"接管"就直接回复** ——
只挂在 take 上的话，那种情况用户的圈会一直转下去。

## D95 ★★ 顺手抓到一个更严重的 bug：人工回复网页访客会静默失败

**现象**：
```json
{"ok": false, "error": "404: 不认识的渠道：web"}
```

**原因**：`_channel_for()` 里是一串并列的 `if platform == ...`，
**加网页渠道时漏了这一处**。

**★★ 为什么这个 bug 特别危险**：
```
· 接管是成功的 ✅
· 队列状态也变成"已接管" ✅
· 只有"发出去"这一步悄悄失败了 ❌
→ 客服以为回了，客户什么都没收到
→ 而且界面上显示"已接管"，看起来一切正常
```

**★ 教训**：
> **"注册新渠道"这种事，最容易漏的就是那种"并列的一串 if"。**
> 它不会在加的时候报错，只在**那个渠道要主动发消息**时才暴露 ——
> 而"主动发消息"只在转人工之后才会用到，所以测试不跑到那一步就发现不了。

**修法**：
1. 补上 `web` 分支
2. 顺手把 `dingtalk` 也加上，但是**如实报 501「还没实现」** ——
   不假装成功（假装的话客服同样会以为发出去了）

# 防崩规范（用户明确要求：不要再崩坏，影响交付）

## 一、崩溃根因（已查清，不是猜的）

| # | 根因 | 证据 |
|---|---|---|
| 1 | **Claude Code 误判模型上下文窗口** | 启动日志原文：「deepseek-v4-flash isn't described by this model catalog; auto-compact keeps this session within **200k tokens** (the context window it assumes)」——实际 deepseek-v4-flash 是 **1M** → 它疯狂 auto-compact，把上下文压了又压 |
| 2 | **上下文涨到 18.6MB** | 单个会话文件 18,991KB；每步要吞 110k+ tokens → 一步等 30 分钟 → 看起来"卡死" |
| 3 | **sleep 轮询等长任务** | Claude 里出现 `sleep 170; tail -6 ...` 多次 → 会话被反复拖长 |
| 4 | **长任务前台跑** | 本机不操作会自动休眠 → 长任务被中断（Claude 自己都去查 powercfg 了） |

## 二、已做的修复

| 修复 | 状态 |
|---|---|
| `CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`（全局 `~/.claude/settings.json` + 项目 `.claude/settings.json`） | ✅ 已写入 |
| 效果 | ✅ 新会话 4.6MB（对比旧会话 18.6MB） |

## 三、防崩纪律（必须遵守）

### A. Claude 侧（写进每份施工指令）
1. **大文件用 Grep + 定向 Read(offset/limit)** —— 绝不整篇读
2. **长输出写文件**，只回贴关键几行
3. **禁止 `sleep` 轮询**等长任务 —— 用后台任务 + 一次性阻塞等
4. **长任务必须后台跑**（本机不操作会自动休眠）
5. **单个 TASK 做完就交报告** —— 不要在一个会话里连做多个 TASK
6. **上下文超过 5MB 主动报告**，由 Hermes 安排重启

### B. Hermes 侧（编排纪律）
1. **每个 TASK 完成立刻 `git commit`** —— 不等全部做完（防丢）
2. **每完成 1~2 个 TASK 就重启会话**（不等上下文涨到 5MB）
3. **每次派单前查会话大小**，>5MB 先重启
4. **重启时用 `docs/会话交接备用.md`**（保持它最新）
5. **关键产物落盘**：`state/` 有 JSON 记录、`D:\sales-report-agent-backup-*` 有全量备份
6. **窗口异常时（标题不更新/CPU 不动/会话不涨）判定崩溃**，走重启流程

## 四、重启流程（2 分钟内完成）

```
1. 查产物：git status（未提交改动还在不在）+ 关键文件是否落地
2. 先 commit 能提交的（防丢），或先备份
3. 关旧窗口 / 杀旧 claude 进程
4. 新窗口：wt.exe -d D:\sales-report-agent cmd /k claude
5. 派交接指令：读 docs/会话交接备用.md + 当前 TASK 的施工指令 → 先摸清现状 → 继续
6. 强调防崩纪律
```

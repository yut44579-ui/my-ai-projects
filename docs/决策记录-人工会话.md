# 人工接管：会话留在人工手上，直到人工主动结束

> 用户的反馈：
> 「我人工那边接管之后，用户这里不能说一句话就人工接管，
>   要人工那边主动说结束了才会结束，
>   然后人工接管同一个人的次数不能太多」

---

## D119 ★★★ 根因：把"一句话处理完了"和"这个会话归人工负责"混成了一件事

**现象**（用户截图）：客服已经接管并回了「你好」，客户又发一句，
右上角又变回「等待人工接入…」，中间又出现「正在为你转接人工客服…」。

**根因**：
```
handover_queue 是**一条问题一条记录**。
客服回复 → reply() 把那条标成 done → 会话"没有人工在管"了
→ 客户下一句 → AI 重新分级 → 又转一次人工 → 用户那边又转起来
```

**★★ 这个 bug 的本质是一个建模错误**：
```
"这条问题处理完了" ≠ "这个会话归人工负责"
```
客服接管的是**这个人/这个会话**，不是那一句话。
他答完一句，会话还在他手上 —— 直到他自己说"结束了"。

**修法**：新增会话级状态表 `human_session`
```sql
status='active' → pipeline 在**任何处理之前**返回 silent，AI 完全不介入
status='ended'  → 交还 AI
```
`pipeline._handover_active()` 现在**优先查这张表**，再退回查队列。

**★ 一个细节**：`reply()` 改成**不设 done**（保持 taken）。
  这样队列里也一直看得到这条，不会因为回了一句就从视野里消失。

## D120 ★★ 接管次数限制：不拦住，而是让它显形

**用户的要求**：「人工接管同一个人的次数不能太多」

**★ 但我没有做成硬拦**：
```
· 拦住不让接管 = 客户没人管，这是拿客户的体验换系统的整洁
· 而且"次数多"本身不是客服的错，是**系统的问题**：
    ① AI 一直答不好他这类问题（该补知识库 / 改分级）
    ② 客服答完就结束、客户又问（该让会话留在人工手上 —— 就是 D119 修的）
```

**做法**：超过上限（默认 24 小时内 3 次）时
```
· 仍然允许接管（客户要被服务）
· 但接口返回一条 warn，工作台上**明确显示**：
  「★ 这个客户已经被转人工 18 次了。多半是 AI 这类问题一直答不好 ——
    建议顺手点「⚠ 报个问题」给技术，比反复人工兜着更省事。」
```

**★ 用滚动窗口不用自然日**：23:59 和 00:01 不该被算成两天。

## D121 ★★ 接管后那条从列表里消失了

**发现方式**：写验证脚本时，点了「接管」但按钮还是「接管」——
一开始以为是前端没刷新，查下去发现是**两个问题叠在一起**：

```
① 后端 /api/handover 默认只查 status='open'
   → 接管后状态变 taken，那条**从列表里消失了**
   ★ 后果比"看不到"更麻烦：客服失去上下文 ——
     他手上正处理的事从视野里没了

② 前端 hoCur 还指着旧对象（status 还是 open）
   → 重渲染之后**还显示「接管」按钮**，客服以为没接管成功，会再点一次
   → 「结束接管」按钮因此永远不会出现
```

**修法**：
```
① 后端默认 open,taken ——"待办" = 没人接的 + 我正在处理的（status 支持逗号分隔）
② hoTake() 里更新本地那条的 status，并 renderHo() 刷新详情
③ 顺手：已经接管了就不再显示「接管」按钮（两个按钮并存会让人以为还要再点）
```

## D122 ★ 「结束接管」必须是人工主动的一个动作

**用户的要求**：「要人工那边主动说结束了才会结束」

**反过来说也成立**：如果系统自己判断"答完了就结束"，
客户下一句就会被 AI 接走 —— 而客服可能只是想歇一下、或者客户话还没说完。

新增 `/api/handover/{id}/end`：
```
· human_session → ended
· handover_queue → done（这才算真正处理完）
· 客户收到"XX已结束本次服务，有问题可以继续问我" → 挂件回到"在线"
```

**前端**：`humanMode` 标记
```
收到 taken / human  → humanMode = true，状态显示"客服在线"
收到 "已结束本次服务" → humanMode = false，回到"在线"
人工模式下发消息     → **不改状态文字**
```
★ 为什么前端也要记：原来 `send()` 无条件把状态改成"正在看…"，
  而人工模式下客户发完消息、客服可能过一会儿才回 ——
  显示"正在看…"会让人以为又是机器人在处理。

## D123 ★ 我之前报的"349 条全通过"是错的

**发现方式**：这次改完跑全量，smoke5 有 2 条失败。
我没有直接改测试让它过，而是**用 git 里的旧版本跑了一遍** ——
一样失败。

```
→ 说明这 2 条**不是这次改出来的**，是更早就坏的
→ 什么时候坏的：我做"人工接管后 AI 沉默"那次
→ 而我当时报了"349 条全通过" —— ★ 那是错的
```

**坏的原因**：smoke5 第 9 步（急停）用 `sim-user` 建了一条 open 的转人工记录，
第 10 步（worker 健壮性）**还是同一个用户** → 被判成"已有人工在管" → 静默
→ 根本没走到发送路径 → 那两条断言没有对象可测。

**修法**：第 10 步改用独立用户
（★ 这不是"改测试让它通过" —— 第 10 步测的是 worker 扛不扛得住发送异常，
  和第 9 步留下的转人工记录本来就不该有关系，是**测试串了状态**）

**★ 教训**：
```
"跑过测试"和"跑过**全部**测试"是两件事。
★ 报数字之前必须真的把全量跑一遍，不能凭印象说"全通过"。
```

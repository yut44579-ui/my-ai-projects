# DECISIONS.md · sales-report-agent

> 每条决策记"选了什么 / 否掉了谁 / 为什么"。面试被问就靠这个。

## D1 · 后端用 FastAPI
- **选**：Python 3.11 + FastAPI
- **否**：Django（太重，功能用不上）、Flask（生态不如 FastAPI 现代）
- **为什么**：轻量、异步、自动文档；本人熟悉；与 pandas/openpyxl 生态无缝

## D2 · 不用 Agent 框架
- **选**：直接调 LLM API（OpenAI SDK 兼容）+ 显式状态机
- **否**：LangChain / LlamaIndex / LangGraph
- **为什么**：流程是固定的几段（解析→确认→固化→执行），不是自主循环；框架会带来黑盒与依赖负担
- **面试答**：够用就不加框架，减少依赖和维护面

## D3 · 不用向量数据库
- **选**：无（不需要语义检索）
- **否**：Chroma / FAISS / Milvus
- **为什么**：需求是结构化字段映射（哪张表哪个字段），不是语义相似检索

## D4 · ★ 数字一律由代码计算（最核心决策）
- **选**：pandas/SQL 计算；LLM 只负责理解需求与写解读
- **否**：让 LLM 直接读数据算数 / 让 LLM 生成 SQL
- **为什么**：LLM 算数不可靠；Spider 2.0 显示真实企业 schema 上 text-to-SQL 准确率仅 **10.1%**；报表的价值就是数字准
- **对照**：开源项目 `ad-report-builder` 同样选择"0 LLM 介入算数"（公式用 Python AST 求值）——行业验证

## D5 · Excel 用 openpyxl 原地改
- **选**：在参考物副本上用 openpyxl 写入
- **否**：pandas.to_excel（重建文件）
- **为什么**：pandas 输出会丢合并单元格/字体/列宽/条件格式；用户要"像这个"
- **对照**：`weekly-report-skill` README 明确写了这个坑

## D6 · 调度用 APScheduler
- **选**：APScheduler（进程内）
- **否**：Celery + Redis（重）、系统计划任务（跨平台麻烦）
- **为什么**：单用户单机，进程内定时够用

## D7 · 前端用原生 HTML/JS
- **选**：单文件 HTML + JS
- **否**：Vue 3 / React
- **为什么**：只有 4 个页面；上次项目用巨型单文件是教训（但那是因为功能太多），这次页面少，反而合适

## D8 · 存储：MySQL + 本地文件
- **选**：MySQL 存任务/记录/字典；产出文件放本地目录
- **否**：对象存储（S3/OSS）、纯文件配置
- **为什么**：单机自用；MySQL 已在本地可用；产出文件用户要能直接打开

## D9 · 首次理解 → 固化（而不是每次重新理解）
- **选**：方案确认后固化成 `task.spec_json`，之后执行不再调 LLM 理解
- **否**：每次用自然语言重新解析
- **为什么**：LLM 有随机性，同样输入可能产出不同报表；报表必须可重复
- **保留**：仍支持"临时用大白话跑一次"的入口

## D10 · 失败不产出错误文档
- **选**：任一步失败 → 记录错误 + 不出文件
- **否**：降级输出（部分数据/空值填充）
- **为什么**：一份"看起来正常但数字错"的报表比没有报表更危险

## 评审后新增/修订（2026-09-21 · 依据 reviews/001 + decisions/001）

### D11 · Report Spec 为项目核心 ★P0
- **选**：自然语言 → AI 解析 → **Report Spec（结构化 JSON）** → 用户确认 → **版本冻结** → 确定性执行
- **为什么**：把"AI 理解"与"代码计算"彻底分离；报表必须可重复（同一 Spec 每次结果一致）
- **执行记录必须绑定**：spec 版本 / 数据快照或查询 / 模板版本 / 代码版本 / execution_id / 校验结果

### D12 · Metric Definition 层（口径先定义）★评审指出的最大风险
- **选**：用 YAML/JSON 定义指标口径（字段、公式、时间口径、排除项），先定口径再计算
- **否**：让 LLM 自己判断"上周销售额"按哪个日期字段
- **为什么**：最大风险不是"AI 理解错"，而是**"语义正确但计算口径错误"**（下单日/支付日/发货日？含退货？含取消单？含税？）

### D13 · 受限 DSL 替代"LLM 生成任意代码"（细化 D4）
- **选**：LLM 只输出受限结构（`sum` / `group_by` / `yoy` / `previous_period` 等 JSON Schema）
- **否**：LLM 生成任意 Python/SQL
- **为什么**：可控、可校验、可审计；避免"看起来对但口径错"

### D14 · 调度必须处理状态（细化 D6）
- **选**：APScheduler + 任务锁 + 重启恢复 + 重复执行保护 + 执行状态记录
- **为什么**：否则"定时自动"只是 demo

### D15 · 前端技术选型（评审意见）
- **选**：原生 HTML/CSS/JS，但**分文件、分层**（api.js 抽接口层 / app.js 视图逻辑 / style.css），不写巨型单文件
- **否**：Vue/React（MVP 4 个页面不值得引入）；也否：2MB 单文件 index.html（旧项目教训）
- **为什么**：架构清晰比框架名重要；评审认可

## D17 · 002B 遗留裁决（2026-09-23）

### D17-1 · 允许 pydantic / fastapi / uvicorn（修正指令矛盾）
- 002A/002B 指令同时写着"用 pydantic v2"和"不引新依赖"——**是 Hermes 的指令矛盾**，Claude 按"显式指定优先"装了 `pydantic 2.13.5`，**处理正确**。
- **最终口径**：`pydantic`（Spec 模型）、`fastapi`+`uvicorn`（002C 接口层）**属于本项目既定技术栈，允许安装**；除此之外不得引入新依赖（无 LangChain / 无向量库 / 无 ORM / 无前端框架）。

### D17-2 · 金额展示口径 = 保留 2 位小数
- 背景：openpyxl 以 `%.16g` 序列化浮点，AC 的严格 `==` 最多到 15~16 位有效数字（ULP 问题）。
- **最终口径**：**内部计算保持全精度**；**写入报表/界面展示保留 2 位小数**（符合报表语义）。002B 已按此实现（报表显示 316412.16）。
- 测试对比口径：比较时用 `abs(a-b) < 1e-6` 或先四舍五入到 2 位，不要求逐位 ULP 相等。

### D17-3 · D16-7 去重策略：**维持"不去重，只报告"**（需用户最终确认）
- Claude 实测影响面（2011-11-21~11-27 那一周）：
  ```
  完全重复行 382 行；重复行金额 1,298.10；占净额 0.421%
  不去重（现状）: 316,412.16
  去重后        : 315,114.06
  ```
- **Hermes 裁决**：**维持现状**（D16 已定"不去重、只报告重复行数"，且影响 0.421%）。
- ⚠️ **这是口径变更**，最终需**用户拍板**；若用户要求去重，须重新评审（改 D16 需走评审流程）。

## D20 · TASK-010 周报：**输出形态**，不是第 6 个计算型 Intent（2026-09-24）

- **背景**：用户问「帮我根据本星期的销售数据做一份销售周报」，系统答的是零散指标卡
  （销售额 / 订单 / 客户 / 客单价 + 口径说明 + 推断段）。数字都对，但**不是一份周报**。
- **选**：`ParsedIntent` 增加 `report: "" | "weekly" | "monthly"` 标记，
  报告 = `sales_compare`（周报 `wow` / 月报 `mom`）+ 四个既有工具的**多段组合输出**
  （`app/ai/report.py` 只编排、不计算；`app/ai/answer.py` 的 `render_report_document`
  只排版）。`COMPUTE_INTENTS` 仍是 **5 个**，`/api/chat/capabilities` 的 `intents` 不增项，
  报告单列在 `report` 块里。
- **否**：做法A —— 新增 `weekly_report` intent + 自己一套周报算法。
  否决理由：① 那等于**第二套口径**（同一个"本周销售额"有两个出处，早晚对不上）；
  ② Intent 数量爆炸（月报、季报、年报…每个都要一个 intent）；
  ③ 周报的本质是**呈现**（比较 + 趋势 + 结构 + 口径 + 结论），不是新的计算。
- **区间不新造**：报告窗口一律走 `tools.resolve_compare_windows`（全项目唯一窗口推导处）。
  周报 = 最近一个**完整**自然周（被数据边界切断就退到最近完整周并写明），月报同理按月；
  用户在问题里写明区间就用用户的（一个字节不动），写了两个以上区间**明确拒绝**、不挑不合并。
  「本星期」这种相对说法**不交给 LLM 翻译** —— 数据最后一天是周五，模型多半会翻出半截周，
  拿 5 天比 7 天得出的"周环比"是假数字。
- **数字来源不变**：报告正文（`what` 段）由代码渲染，LLM 只写【为什么】/【建议行动】，
  照旧过后置数字闸门（`number_guard` / `currency_guard`）；模型写错就整段作废，
  报告正文**一个字节都不动**。
- **导出**：`answer.export` = Markdown（同一份文档 + 结论段 + 币种/数据范围脚注）。
  前端页面上预览的与点「下载 Markdown」拿到的是**同一段文本**（零依赖 Blob 下载，
  不新增后端端点、不引 CDN）。Excel 导出后置。
- **可追溯**：`report_document` 随记录落盘（文档结构可事后逐段复算），
  报告级 `facts` 里五个工具的本期总额做**交叉对账**，不相等就不发报告。

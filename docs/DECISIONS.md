# 决策记录（已冻结，勿改）

D1 复用策略：同约定最小重写；禁止抽公共包；禁止跨项目 import（sales-report-agent 只作参考）
D2 技术栈：MySQL8 + FastAPI + SQLAlchemy 2.x + Alembic + React+TS+Vite+AntD（见上）
D3 V1 单租户：不做 tenants；但 Repository 层保留 scope 参数作为迁移口
D4 数据契约：所有业务数字必须返回 EvidenceValue = {value, state, source_type, evidence_ref}
   state 三态：VALID（value 可为 0）/ NO_DATA（value=null）/ ERROR —— 三者绝不能混
   前端禁止自己算业务数字（不许 customers.length 显示成"客户数"）
D5 证据锚点：风险证据用 message_id 作为锚点，trigger_text 只作摘要
D6 汇报用生成时快照，不用实时重算；时区固定 Asia/Shanghai
D7 AI 安全拦截必须在代码层（Prompt 只负责表达，不负责安全）
   必须人工：报价/折扣/合同承诺/大额订单/付款/退款/银行账户/赔偿/法律承诺/
             重大投诉/特殊资源承诺/高价值客户关键承诺/异常资金
   「建议」≠「执行」："建议给 8 折"可作 SUGGESTION；"已经给你申请 8 折" 必须人工
D8 人工接管状态机：AUTO → HUMAN_REQUIRED → HUMAN_ACTIVE（不做工作流引擎）
D9 禁止伪造客户消息：站内没有真实客户渠道时，不许把客户没发过的消息写成 CUSTOMER
D10 AI 调用失败必须如实显示"AI 暂时无法回复，请人工处理"，禁止编造 AI 回复
D11 V1 数据模型冻结 7 表：users / customers / customer_messages / customer_events /
    risk_events / import_batches / reports（TASK-001 已落 customers + import_batches 两张）

—— 以下为 TASK-001 落地时的补充决策（追加，不改上面已冻结的内容）——

D12 去重口径（TASK-001 §二 与 AC3c 冲突的处置）：
    §二 写"0 条候选 → CLEAN"，AC3c 要求"email/phone 都空的两行各自 PENDING_REVIEW"。
    两者只在"有没有可比的键"上有分歧。取 AC 口径并细分：
      有键、查不到 → CLEAN（确实是新客户）；压根没有键可比 → PENDING_REVIEW（无法判重，交人工）。
    「空值绝不参与匹配」这条不动：空值根本不构造查询条件。

D13 文件级失败不落 import_batches 行（"零入库"的最严解释）：
    空文件/格式不支持/超限/解析失败等一律 400 + 错误码，不留半截批次记录，
    因此同一份文件修好后可以重传，不会被自己的幂等检查挡住。FAILED 枚举保留在类型里。

D14 TASK-001 只新增两个依赖，均有不可替代的理由（硬边界：不引重型依赖）：
    · openpyxl —— xlsx 是 zip+XML 容器，标准库无解析器；用成熟库不自己造轮子。
    · python-multipart —— FastAPI 接收 multipart 文件上传的必需依赖。
    ★ 刻意不引 pandas：CSV 用标准库 csv、单元格统一 str 化，
      从根上杜绝"自动类型推断把电话读成科学计数/丢前导零"。

D15 跳过原因的层级：missing_name / invalid_phone / invalid_email / empty_row 用于**行级**
    （skipped_reasons_json）；unmapped_column 用于**列级**（skipped_columns_json）。
    两者共用同一个冻结枚举，不新增自由文本。

D16 customers.first_seen_at / last_seen_at 在 MySQL 上用 DATETIME(6)：
    DATETIME 默认只到秒，"命中即刷新 last_seen_at"在同一秒内无法观测，语义会被吃掉。

D17 沟通记录（TASK-003）的三条落地口径：
    ① D9 的「禁止伪造客户消息」落成**两道闸门**：services/messaging.py 的 write_message()
       直接拒绝 sender_type=CUSTOMER（任何代码路径都写不进去），接口层再翻译成
       400 + customer_sender_forbidden（明确错误码）。CUSTOMER 枚举保留，留给将来的真实客户渠道。
    ② 规格写的「只允许写 HUMAN / SYSTEM / IMPORT」在本表上的含义：
       sender_type 枚举（规格冻结）里没有 IMPORT，所以 HUMAN=人工、SYSTEM=系统产生、
       "随导入带入"落在 message_type=IMPORT 上（此时 source_type 记 IMPORT）。
    ③ 时间线排序键是 (created_at, id) 双键正序；created_at 与 customers 一样用 DATETIME(6)，
       同一秒内的多条消息也能稳定排出先后（理由同 D16）。

D18 AI 回复（TASK-004）的四条落地口径：
    ① 闸门是**纯代码函数**（services/policy_gate.py 的 evaluate_policy），判定词表写死在代码里，
       模型完全不参与"要不要转人工"的判断（D7）。命中 → 不调 LLM，直接落 HUMAN_REQUIRED。
    ② 二次把关：LLM 生成完的草稿**再过一次同一个闸门**。
       模型自己写出的"已经给你 8 折"这类对外承诺一样拦下：草稿不落库，改落 HUMAN_REQUIRED
       （宁可丢一条草稿，也不让承诺出街）。
    ③ 客户问题从哪来：站内没有真实客户渠道（D9），所以 ai-reply 的入参是
       content（人工把客户原话贴进来）或 in_reply_to（指向该客户下已录入的一条消息）；
       **任何路径都不写 sender_type=CUSTOMER**。
       转人工说明 / LLM 失败兜底都用 sender_type=SYSTEM + message_type=NOTE：
       这一轮既然没有 AI 回复，就不许留一行看起来像 AI 说的话。
    ④ LLM 失败（未配 key / 超时 / 非 200 / 空内容）→ 502 + {"error":"llm_unavailable"}，
       message 固定为「AI 暂时无法回复，请人工处理」，同时库里落一行 FAILED。
       ★ 绝不允许拿别的内容冒充 AI 回复（D10）；只引 httpx，不引任何 LLM SDK。

D20 客户访问不新建表（TASK-010）：记为 customer_events 的新事件类型 VISIT。
    ① 理由：D11 冻结 7 表；访问本质是「客户发生了什么」，与状态变更/消息/接管同类；
       metadata_json 足以承载 page / channel / referrer，不必为此建表（§五 能简不繁）。
    ② **只记可识别到客户的访问**（§十）：接口必须给 customer_id，匿名访问不落库 ——
       记下来既不能算指标也不能驱动跟进，还会污染客户动态。
    ③ actor_type=SYSTEM：这是客户侧行为被系统记录，不许写成 AI（否则
       「AI 不许自行改状态」那条边界会被污染）。
    ④ ★ MySQL 的 ENUM 列是**字面量列表**，在 Python 侧往 Enum 加成员**不会**改变列定义，
       Alembic autogenerate 也检测不到 → 必须手写迁移 ALTER TABLE MODIFY COLUMN。
       不迁移直接插 VISIT 会报 1265 "Data truncated"（实测踩过）。

D21 市场研究只做字面统计（TASK-011）：
    ① 本页**不调用 LLM**。市场结论属 §三 的 INFERENCE，没有真实市场数据时模型只能编。
    ② 占比（share）只在样本量 ≥ 10 时给出，否则返回 null（界面显示「—」）：
       3 个客户算出「33.3%」会被误当成市场结论。
    ③ 「行业词频」是**数字面词**（公司名里出现 ≥2 次、去掉"有限公司"等通用词），
       不是 AI 行业归类。它不会把「深圳前海科技」归到「金融科技」，也绝不会编出行业。
    ④ 页面显式声明**答不了**的范围（竞对/市场规模/外部趋势），而不是回避。

D22 数据分析（TASK-012）：
    ① 漏斗用**累计口径**（达到或超过该阶段）。lifecycle_status 是离散状态不是阶段进度，
       直接按当前状态计数会得出「已成交 0 但已报价 2」这种越往后越大的错结论。
       已失效(LOST) 是旁支终态，不进漏斗主线。
    ② 「算不了」与「算出来是 0」严格区分：分母为 0 或样本不足 → null（界面「—」）；
       分母非 0 且确实没人转化 → 0.0（这是有意义的结论）。这是 D4 三态原则的应用。
    ③ 趋势按 Asia/Shanghai 归日（D6）。★ 用 UTC 归日会把凌晨的「今天」漏出区间（实测踩过）。

D29 ★ 认证规格定稿（TASK-015，取代 D25）
    ① 项目文档原先对登录/密码/会话/权限**零规格**（D25 据此决定不做）。
       项目负责人明确选择「做完整登录」，故本轮先定规格再实现：
       规格正文见 **docs/AUTH_SPEC.md**（范围/数据模型/口令存储/会话/失效/受保护范围/前端/初始化）。
    ② 关键取舍（都在规格里给了理由）：
       · 口令用标准库 **PBKDF2-HMAC-SHA256**（21 万次迭代、每用户独立盐、恒定时间比较），
         不引 bcrypt/argon2 第三方依赖（§五 能简不繁）。
       · 会话用**自签 HMAC 令牌**，不引 JWT 库、**不建 sessions 表**（否则第 11 张表）。
       · 无状态令牌的代价用 `users.token_version` 补：改密码/停用/踢下线时自增，

       · 只做两级角色（ADMIN/MEMBER），不做权限矩阵；**不做注册**（账号由管理员创建）。
       · D3「V1 单租户」不变：这是单租户内的多用户，不是多租户。
    ③ D25 保留为历史记录，不再生效。

D30 认证落地（TASK-019）：★ D11 冻结 7 表至此 **7/7 全部建成**（users 是最后一张）。
    ① 按 docs/AUTH_SPEC.md 实现，实现中确认的四条口径：
       · 登录失败**不区分**"用户名不存在"与"口令错误"，返回同一句话 ——
         区分会泄露哪些用户名存在，等于给撞库的人送情报。
       · 用户名统一**小写存储**，避免 Admin 与 admin 变成两个账号。
       · **不提供注册接口**（AUTH_SPEC §1/§9），首个管理员由 scripts/create_admin.py 创建，
         避免部署后被人抢先注册管理员；种子账号**不写进迁移**（迁移在仓库里，塞默认口令是反模式）。
       · 不允许管理员**停用自己**：否则会把自己锁在门外且没有其它途径恢复。
    ② 受保护范围用「默认全保护 + 显式放行」实现（api/router.py 分 public/protected 两组）：
       逐条给路由加鉴权依赖有两个真问题 —— 漏加一条就是**未鉴权的后门**且难发现；
       新增路由时靠"记得加"不可靠。现在**新增业务路由默认就是受保护的**（安全的默认值）。
       放行清单只有 /health 与 /auth/login。
    ③ token_version 机制实测有效：停用账号 / 重置口令后，**已发出的令牌立即 401**
       （不是等过期）。这是无状态令牌必须补的失效入口。
    ④ ★ 401 与 403 严格分工：401 = 没登录/令牌无效/已失效；403 = 已登录但角色不足。
    ⑤ AUTH_SECRET_KEY 未配置时**拒绝鉴权**（500 + auth_not_configured），
       不提供任何默认密钥 —— 偷偷用弱默认值比不做鉴权更危险（所有人都能伪造令牌）。

    ③ 切片独立成表（而非存 JSON）的三个理由：检索要返回**片段级**结果；
       每片段要能作为**证据锚点**；LIKE 检索需要 content 是真实列。
    ④ ★★ **切片偏移必须精确 —— 本轮踩的坑（重点记）**：
       第一版实现把若干 `strip()` 过的段落**拼接**成切片内容，同时用原始区间做偏移，
       结果 `text[char_start:char_end] != content`（空白差异导致端到端对不上），

       ★ 通用教训：**只要对外声称"可回溯/可定位"，就必须让这个声称可被断言验证**，
         否则它只是注释里的一句好话。

D58 实时在线状态：心跳 + 活动检测（TASK-040）
    ① 用户要求：「状态那里我希望是实时变化的，就是在线/忙碌/离线等」。
       ★ 这**推翻了 TASK-037（D54③）的做法** —— 那时我做的是"用户自己设置"的
         自我声明，并在界面上如实写明"系统没有实时在线探测"。
         用户明确要求改成真的会自己变，所以现在把它真正做出来。
       ★ 顺带说明：D54③ 那条"如实声明没有探测"当时是对的（确实没有），
         现在实现了探测，所以那些文案**必须一起改** ——
         否则界面会说"没有实时探测"而实际有，同样是界面说谎。
    ② ★★ **判定规则**（原文暴露给前端，界面上逐条展示）：
         在线  最近 5 分钟内有操作（鼠标/键盘/滚动/切回标签页）
         忙碌  页面还开着（心跳正常），但超过 5 分钟没有操作
         离线  超过 90 秒没有心跳（页面关闭或网络中断）
       · 心跳间隔 30 秒；离线阈值取 3 倍（容忍一次丢包/切网，否则状态会来回跳）
       · 空闲阈值 5 分钟：正常阅读思考不会误判，离开工位则会
    ③ ★★ **为什么分「心跳」与「操作」两个时间戳**：
         · 只发心跳 → 人离开工位但页面没关，系统一直认为他"在线"，
           同事找人找不到，这个状态是错的
         · 只看操作 → 切到别的窗口就误判成离线
         两者结合才有有意义的三态（这也是常见 IM 的做法）。
       实现：last_seen_at（页面还开着）+ last_active_at（人在操作）。
    ④ ★★ **状态是「推算」而不是「存储」**：
       读的时候按时间戳现算，不写 users.presence。
       · 存下来的结果在两次扫描之间必然是旧的；推算的结果永远最新
       · 存的话还得有定时任务不停扫描 —— 那需要 Celery/cron（本项目刻意没上）
       ★ 代价是每次读用户列表都算一遍，纯内存减法，相比查询可忽略。
    ⑤ ★ **手动覆盖保留，但必须带到期时间**（30/60/180 分钟）：
       系统观测不到"在开会/外出"，只能观察到「页面开着但没动静」，
       所以覆盖是对观测盲区的补充，不是取代。
       ★ 必须有到期：手动设的"忙碌"若永不过期，人会忘了改，状态永远是错的 ——
         那比没有这个功能更糟。
       ★ 心跳**不解除覆盖**（实测：覆盖期间发 active 心跳仍为忙碌）——
         否则用户设了"忙碌 1 小时"，一刷新就变回在线，设置形同虚设。
    ⑥ ★ **关闭页面主动上报离线**：用 etch(..., {keepalive:true})
       **而不是** 
avigator.sendBeacon —— sendBeacon 不能自定义请求头，
       只能把令牌塞进 URL，那会让凭据出现在服务器访问日志里。
       实测：leaving=true 把状态立刻置为离线，同事不用等 90 秒超时。
    ⑦ 界面：顶栏状态点**活的**（心跳回调直接更新，不用刷新页面）；
       头像下拉里状态变为**只读展示 + 依据**，不再可点选
       （自动推算与手动点选会打架，想覆盖请去个人中心）；
       用户与权限列表加头像 + 状态圆点，能看同事在不在线。
    ⑧ ★ 实测状态随时间自动变化（改的是时间戳，不是状态字段）：
         刚有操作            → 在线  「刚刚有操作」
         4 分钟前有操作       → 在线  「4 分钟前有操作」
         7 分钟前有操作       → 忙碌  「页面开着，但已 7 分钟没有操作」
         120 秒前心跳         → 离线  「已有 2 分钟没有心跳」
    ⑨ ★ 断言同步改了：原断言写的是「说明状态是自己设置的不是探测」，
       现在是**错的**。已改为验证「自动推算」「判定规则」「当前依据」
       「临时覆盖入口」。再次印证 D52④ 的教训：**断言要跟着行为改**。

D59 表单 AI 辅助填写：只生成「描述性文字」，不生成「事实性输入」（TASK-042）
    ① 用户需求：「这些填写内容的都需要有 ai 生成的功能」（指各新建表单的文本字段）。
    ② ★★ **这条线必须划清，否则整个系统「不编造」的根基就没了**：
       ✅ 可生成（描述性/组织性文字）：项目说明、商机备注、研究要点、建议动作、跟进记录
       ❌ 不能生成（事实/证据/判断）：
          · **线索研究的「公开资料原文」** —— 最关键的一条。
            整条链是「AI 只从**你贴的真实原文**里抽事实，每条引用逐字回验，
            原文里找不到的一律删除」。如果原文本身是 AI 写的，
            回验就变成自己验证自己编的东西，那份研究和它的所有下游结论全部失效。
          · 客户需求 / 背景 —— 是客户真实说过的话，编了等于伪造需求
          · 金额 / 折扣 / 账期 / 概率 / 进度 —— 是事实数字或人的判断
          · 联系方式 —— 是事实
    ③ ★★ **白名单由后端决定，不由前端各页自己判断**：
       新增 GET /api/ai/draft-fields 返回「可生成字段」+「刻意排除的字段及原因」。
       前端据此决定按钮出不出现 ——
       ★ 不能生成的字段**根本不显示按钮**，并在标签旁写「无 AI（需真实内容）」。
         比"显示了按钮再弹窗拒绝"好：用户不会问"为什么这里没有 AI"。
    ④ **研究要点是新增字段**（prospect_research.focus，迁移 22）：
       ★ 它与 source_text 必须**分开存、分开显示**：
           focus       = 人的**提问**（要查证什么）—— 允许 AI 起草，它本来就是待验证的
           source_text = 真实的**证据**（公开资料原文）—— 绝不允许 AI 生成
         混在一个字段里就会把「AI 编的问题」当成「已核实的资料」。
         界面上也是两块：要点单独一张卡片，原文在折叠区里。
    ⑤ 提示词铁律：只使用给定信息；不许补金额/折扣/工期/客户名/联系方式；
       不许用「预计/大约」凑字数；不许承诺效果；**不许写任何前缀标题**
       （实测第一版会输出「商机备注：」，已加规则 4 修掉）；

    ⑥ ★ **生成结果只是草稿**：只填入输入框，不直接提交、不写库 ——

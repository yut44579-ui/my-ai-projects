# DECISIONS.md · sales-report-agent

> 每条决策记"选了什么 / 否掉了谁 / 为什么"。面试被问就靠这个。

## D1 · 后端用 FastAPI
- **选**：Python 3.11 + FastAPI
- **否**：Django（太重，功能用不上）、Flask（生态不如 FastAPI 现代）
- **为什么**：轻量、异步、自动文档；本人熟悉；与 pandas/openpyxl 生态无缝

## D2 · 不用 Agent 框架
- **选**：直接调 LLM API（OpenAI SDK 兼容）+ 显式状态机
- **否**：LangChain / LlamaIndex / LangGraph
- **为什么**：流程是固定的几段（解析→确认→固化→执行），不是自主循环；框架会带来黑盒与依赖负担
- **面试答**：够用就不加框架，减少依赖和维护面

## D3 · 不用向量数据库
- **选**：无（不需要语义检索）
- **否**：Chroma / FAISS / Milvus
- **为什么**：需求是结构化字段映射（哪张表哪个字段），不是语义相似检索

## D4 · ★ 数字一律由代码计算（最核心决策）
- **选**：pandas/SQL 计算；LLM 只负责理解需求与写解读
- **否**：让 LLM 直接读数据算数 / 让 LLM 生成 SQL
- **为什么**：LLM 算数不可靠；Spider 2.0 显示真实企业 schema 上 text-to-SQL 准确率仅 **10.1%**；报表的价值就是数字准
- **对照**：开源项目 `ad-report-builder` 同样选择"0 LLM 介入算数"（公式用 Python AST 求值）——行业验证

## D5 · Excel 用 openpyxl 原地改
- **选**：在参考物副本上用 openpyxl 写入
- **否**：pandas.to_excel（重建文件）
- **为什么**：pandas 输出会丢合并单元格/字体/列宽/条件格式；用户要"像这个"
- **对照**：`weekly-report-skill` README 明确写了这个坑

## D6 · 调度用 APScheduler
- **选**：APScheduler（进程内）
- **否**：Celery + Redis（重）、系统计划任务（跨平台麻烦）
- **为什么**：单用户单机，进程内定时够用

## D7 · 前端用原生 HTML/JS
- **选**：单文件 HTML + JS
- **否**：Vue 3 / React
- **为什么**：只有 4 个页面；上次项目用巨型单文件是教训（但那是因为功能太多），这次页面少，反而合适

## D8 · 存储：MySQL + 本地文件
- **选**：MySQL 存任务/记录/字典；产出文件放本地目录
- **否**：对象存储（S3/OSS）、纯文件配置
- **为什么**：单机自用；MySQL 已在本地可用；产出文件用户要能直接打开

## D9 · 首次理解 → 固化（而不是每次重新理解）
- **选**：方案确认后固化成 `task.spec_json`，之后执行不再调 LLM 理解
- **否**：每次用自然语言重新解析
- **为什么**：LLM 有随机性，同样输入可能产出不同报表；报表必须可重复
- **保留**：仍支持"临时用大白话跑一次"的入口

## D10 · 失败不产出错误文档
- **选**：任一步失败 → 记录错误 + 不出文件
- **否**：降级输出（部分数据/空值填充）
- **为什么**：一份"看起来正常但数字错"的报表比没有报表更危险

## 评审后新增/修订（2026-09-21 · 依据 reviews/001 + decisions/001）

### D11 · Report Spec 为项目核心 ★P0
- **选**：自然语言 → AI 解析 → **Report Spec（结构化 JSON）** → 用户确认 → **版本冻结** → 确定性执行
- **为什么**：把"AI 理解"与"代码计算"彻底分离；报表必须可重复（同一 Spec 每次结果一致）
- **执行记录必须绑定**：spec 版本 / 数据快照或查询 / 模板版本 / 代码版本 / execution_id / 校验结果

### D12 · Metric Definition 层（口径先定义）★评审指出的最大风险
- **选**：用 YAML/JSON 定义指标口径（字段、公式、时间口径、排除项），先定口径再计算
- **否**：让 LLM 自己判断"上周销售额"按哪个日期字段
- **为什么**：最大风险不是"AI 理解错"，而是**"语义正确但计算口径错误"**（下单日/支付日/发货日？含退货？含取消单？含税？）

### D13 · 受限 DSL 替代"LLM 生成任意代码"（细化 D4）
- **选**：LLM 只输出受限结构（`sum` / `group_by` / `yoy` / `previous_period` 等 JSON Schema）
- **否**：LLM 生成任意 Python/SQL
- **为什么**：可控、可校验、可审计；避免"看起来对但口径错"

### D14 · 调度必须处理状态（细化 D6）
- **选**：APScheduler + 任务锁 + 重启恢复 + 重复执行保护 + 执行状态记录
- **为什么**：否则"定时自动"只是 demo

### D15 · 前端技术选型（评审意见）
- **选**：原生 HTML/CSS/JS，但**分文件、分层**（api.js 抽接口层 / app.js 视图逻辑 / style.css），不写巨型单文件
- **否**：Vue/React（MVP 4 个页面不值得引入）；也否：2MB 单文件 index.html（旧项目教训）
- **为什么**：架构清晰比框架名重要；评审认可

## D17 · 002B 遗留裁决（2026-09-23）

### D17-1 · 允许 pydantic / fastapi / uvicorn（修正指令矛盾）
- 002A/002B 指令同时写着"用 pydantic v2"和"不引新依赖"——**是 Hermes 的指令矛盾**，Claude 按"显式指定优先"装了 `pydantic 2.13.5`，**处理正确**。
- **最终口径**：`pydantic`（Spec 模型）、`fastapi`+`uvicorn`（002C 接口层）**属于本项目既定技术栈，允许安装**；除此之外不得引入新依赖（无 LangChain / 无向量库 / 无 ORM / 无前端框架）。

### D17-2 · 金额展示口径 = 保留 2 位小数
- 背景：openpyxl 以 `%.16g` 序列化浮点，AC 的严格 `==` 最多到 15~16 位有效数字（ULP 问题）。
- **最终口径**：**内部计算保持全精度**；**写入报表/界面展示保留 2 位小数**（符合报表语义）。002B 已按此实现（报表显示 316412.16）。
- 测试对比口径：比较时用 `abs(a-b) < 1e-6` 或先四舍五入到 2 位，不要求逐位 ULP 相等。

### D17-3 · D16-7 去重策略：**维持"不去重，只报告"**（需用户最终确认）
- Claude 实测影响面（2011-11-21~11-27 那一周）：
  ```
  完全重复行 382 行；重复行金额 1,298.10；占净额 0.421%
  不去重（现状）: 316,412.16
  去重后        : 315,114.06
  ```
- **Hermes 裁决**：**维持现状**（D16 已定"不去重、只报告重复行数"，且影响 0.421%）。
- ⚠️ **这是口径变更**，最终需**用户拍板**；若用户要求去重，须重新评审（改 D16 需走评审流程）。

## D20 · TASK-010 周报：**输出形态**，不是第 6 个计算型 Intent（2026-09-24）

- **背景**：用户问「帮我根据本星期的销售数据做一份销售周报」，系统答的是零散指标卡
  （销售额 / 订单 / 客户 / 客单价 + 口径说明 + 推断段）。数字都对，但**不是一份周报**。
- **选**：`ParsedIntent` 增加 `report: "" | "weekly" | "monthly"` 标记，
  报告 = `sales_compare`（周报 `wow` / 月报 `mom`）+ 四个既有工具的**多段组合输出**
  （`app/ai/report.py` 只编排、不计算；`app/ai/answer.py` 的 `render_report_document`
  只排版）。`COMPUTE_INTENTS` 仍是 **5 个**，`/api/chat/capabilities` 的 `intents` 不增项，
  报告单列在 `report` 块里。
- **否**：做法A —— 新增 `weekly_report` intent + 自己一套周报算法。
  否决理由：① 那等于**第二套口径**（同一个"本周销售额"有两个出处，早晚对不上）；
  ② Intent 数量爆炸（月报、季报、年报…每个都要一个 intent）；
  ③ 周报的本质是**呈现**（比较 + 趋势 + 结构 + 口径 + 结论），不是新的计算。
- **区间不新造**：报告窗口一律走 `tools.resolve_compare_windows`（全项目唯一窗口推导处）。
  周报 = 最近一个**完整**自然周（被数据边界切断就退到最近完整周并写明），月报同理按月；
  用户在问题里写明区间就用用户的（一个字节不动），写了两个以上区间**明确拒绝**、不挑不合并。
  「本星期」这种相对说法**不交给 LLM 翻译** —— 数据最后一天是周五，模型多半会翻出半截周，
  拿 5 天比 7 天得出的"周环比"是假数字。
- **数字来源不变**：报告正文（`what` 段）由代码渲染，LLM 只写【为什么】/【建议行动】，
  照旧过后置数字闸门（`number_guard` / `currency_guard`）；模型写错就整段作废，
  报告正文**一个字节都不动**。
- **导出**：`answer.export` = Markdown（同一份文档 + 结论段 + 币种/数据范围脚注）。
  前端页面上预览的与点「下载 Markdown」拿到的是**同一段文本**（零依赖 Blob 下载，
  不新增后端端点、不引 CDN）。Excel 导出后置。
- **可追溯**：`report_document` 随记录落盘（文档结构可事后逐段复算），
  报告级 `facts` 里五个工具的本期总额做**交叉对账**，不相等就不发报告。

## D21 · 账号审批与游客限制：第一个账号是管理员、受限只在前端拦（2026-09-25）

- **背景**：用户要求账号**真入库**、注册之后**要管理员批准**才让登录、并给游客身份
  划一条清楚的线（能用只读浏览，不能导入 / 导出 / 改任务 / 管账号 / 删除）。
  两个关键点用户直接拍了：**第一个注册的账号自动成为管理员**、「账号管理」放**系统设置**里。
- **为什么第一个必须是管理员**：如果新账号一律等批准，而这台机器上还没有任何账号，
  就没有人能按下"批准"，系统**当场死锁**。所以规则是
  `role = admin if 系统里还没有 admin else user`，且第一个账号直接 `active`。
  它不是"特权"，是**唯一能开锁的那把钥匙**。
- **角色只有一种升级路径**：只有"第一个注册的"这一条。审批（`review`）只改 `status`，
  **不改 `role`** —— 于是系统里永远只有一个管理员，也就不存在"谁该有管理权"的争议；
  代价是管理员账号**不可停用 / 不可删除**（否则没人能批账号）。这条保护在三处都写了：
  `accounts.review`、`accounts.delete_account`、`api_auth` 的删自己守卫。
- **四种"登不上"必须说四句不同的话**（用户点名要能逐个分辨）：
  待批准 403 / 未通过审批 403 / 已停用 403 / 密码错 401 —— 前三种是
  **"你没被允许"**，最后一种才是**"你没通过校验"**，HTTP 语义与文案都分开。
  顺序上**先验密码、再看状态**：否则"待批准"这句话就成了"这个账号存在吗"的探针。
- **★ 游客限制是前端拦的，必须说清楚**：legacy 端点（`/api/upload`、`/api/tasks`、
  导出…）是**冻结契约**，不按账号鉴权，也不能为了鉴权给它们加必填头（那就改了契约）。
  所以"游客不能导入/导出/改任务"由 `web/session.js::guard()` 在前端**硬拦**
  （返回 false → 调用方立刻 return → 请求不发、文件不下载），
  执行处与入口按钮**两处都拦**（只拦按钮会被"从别处调这个函数"绕过去）。
  **真正在服务端拦住的**是账号管理那三条（列表 / 审批 / 删除）：游客没有会话编号 → 401、

## D22 · FR-002A 本机单用户模式：注册即生效 + 启动迁移（2026-09-28）

- **背景**（用户原话）：「我这边是管理员，**你不要把我的账号以及密码，在正确的情况下或者
  注册的情况后，让我还要去通过审批**。我找谁审批？**我自己弄的，我还要去找别人审批啊**」。
  实测复现的死锁：库里已有一个 `active` 管理员（早期测试账号，密码用户不知道），
  用户新注册的账号于是 `pending` —— **没有任何人能批准它**，用户被自己的系统锁在门外。
- **选**：**模式决定要不要审批**（裁决 A）。
  `SRA_REQUIRE_APPROVAL` 未设/空/`0`（**默认**）= 本机单用户：注册即 `active`，
  第一个账号 `admin`、其余 `user`，谁都不用批；置 `1` 才走真实审批流
  （`pending` → 已生效的管理员批准 → `active`）。
- **否**：① 造一个"能绕过审批的管理员"（那是特权后门，不是修复）；
  ② 用账号名 / IP / localhost / 浏览器 Cookie 证明"你是本机所有者"（都不构成所有权证明，
  且等于又造一套登录系统）；③ 引入 `instance_owner_secret` 之类的第二套凭据体系。
- **为什么默认是本机单用户**：本项目就是**单用户、单机、自用**（CLAUDE.md 目标用户 = 本人）。
  在这个前提下，"注册要别人批"没有任何可执行的审批人 —— 默认值必须让系统**可用**，
  要审批的单位再显式打开。这条与 D21"第一个账号是管理员"是同一条思路的延伸：
  D21 解决"库是空的时候死锁"，D22 解决"库里已经有个够不着的管理员时死锁"。
- **启动迁移**（`app/accounts.py::migrate_accounts`，接在 FastAPI lifespan 最前面）：
  ① 库里已有可用管理员 → `pending` 升 `active`，**role 一个都不改**；
  ② 一个可用管理员都没有 → 最早的账号升 `admin`+`active`（优先"本来就写着 admin 的记录"，
  这样不会多出第二个 admin），其余 `pending` 升 `active`。
  幂等（`set_account_status` 本身"没变不写盘"）、留痕（写 `reviewed_by`/`reviewed_at`）、
  **不删账号、不碰 `pwd_*`**、失败不拦服务启动（读不出账号表就如实记错并放弃）。
- **真实审批流模式（`=1`）下不替管理员按"批准"**：有可用管理员时迁移什么都不做；
  只有"一个可用管理员都没有"时才动手 —— 那时不是"该不该批某人"，而是已没人能批账号。
- **`pending` 状态保留不动**：审批流每一行代码、每一句话都还在，只是默认不走那条路
  （`test_fr002a_local_mode.py::test_A9` 钉住这一点）。
- **对既有测试的处理（如实记录）**：`tests/test_auth_admin.py` 与
  `tests/test_fr001a_recovery.py` 的前置条件都是"第二个账号 = 待批准"，
  它们是**审批流**那一套测试 —— 两个 fixture 里显式 `SRA_REQUIRE_APPROVAL=1`，
  **断言一条没改**；`test_auth.py` 里那句 `review(approve)` 改成"只有 pending 才批"的
  小工具（它的注释本来就写着那一步只是为了"让第二个账号能登录"）。
  本机单用户模式自己的验收在新文件 `tests/test_fr002a_local_mode.py`。
- **前端同步**（`web/session.js` / `web/index.html`）：注册结果改成按**后端给的状态**分支
  —— `active`+`admin`（第一个账号）与 `active`+`user`（本机单用户）都能直接进系统，
  只有 `pending` 才显示"等待批准"那张卡片；登录页与帮助里"注册后需管理员批准"的硬说法
  改成如实描述两种模式。**流程本身没动**（还是"注册 → 按状态决定进不进系统"）。
- **遗留（明确记录，未做）**：前端不读那个环境变量（页面不显示"当前是哪种模式"），
  用户要判断模式只能看 `.env`；管理员**授予**别人管理员身份仍未做。

## D23 · FR-003 多格式导入 + 地区维度：**来源链**与**数据驱动维度**（2026-09-29）

- **背景**（用户原话）：①「外部 Excel / PPT / Markdown 导入进来，**真的存进数据库**」；
  ②「地区维度……**不要有国家这种**」「**各个地区的就行了**」。
- **选**（一）：**三层来源链** `source_file → import → {dataset | document}`。
  一份文件进系统只登记**一次** `source_file`（按内容 SHA-256）；一次导入尝试写一条 `import`
  审计记录（成功/失败/幂等跳过都留痕）；解析产物按文件类型落成 `dataset`（表格类）
  或 `document`（资料类）。**同一份文件两种产物都有时，它们共享同一个 `source_file_id`**
  —— 这就是"一份 PPT 里既有表格又有正文，两边都进得去、又可追溯"的实现方式。
- **选**（二）：**SQLite 只做持久化，不做计算**。8 张表里 `dataset_rows` 一行一条
  （行内容整体存 JSON `payload`），查询只允许 `SELECT payload`；任何 SUM/GROUP BY/AVG
  都不许出现在 SQL 里 —— 取出的行交给 pandas，走既有的确定性计算层。
  这是铁律 1（数字一律由代码算）在多格式导入这条线上的直接推论：
  换了存储不等于换了计算引擎，**计算口径只有一份**。
- **否**：① **绝不用 `Country` 冒充地区**。地区维度的候选字段来自**数据源本身**，
  字段名里出现「国家 / Country / 国别」的列**直接被排除在地区类之外**
  （`app/importer/regions.py::_NEVER_REGION`）。数据源里没有地区字段时，
  接口返回结构化错误 `DIMENSION_UNAVAILABLE`（`code/dimension/message` 提到顶层），
  **不回退、不猜、不拿国家顶上**。
  ② 不引入 OCR / LibreOffice / Pandoc / Office COM / Java / 浏览器运行时来读 PPT
  （评审红线）—— PPTX 走 `python-pptx`（唯一新增依赖，见 requirements.txt 里那段说明）。
  ③ 不把 SQLite 做成第二个计算引擎，不做 SQL 聚合业务指标。
  ④ 不引入向量库 / RAG / embedding（D3 不变）。
- **地区维度的识别规则**（`regions.py`，四条同时成立才算）：
  ① 字段名命中地区词表（region/area/地区/区域/省份/省/城市/市/区县…），
     且**不是**国家词、**不是**人名式短语（「区域经理」不算 —— 它是人不是地区）；
     单字关键字（省/市/区）只允许精确相等或 ≤4 字的"地名后缀"匹配，不许按子串乱匹配；
  ② 非空占比 ≥ 0.5；③ 取值个数 2 ≤ n ≤ 200；④ 离散文本、平均长度 ≤ 20 字。
  分类上 **`region / province / city / district` 才算地区类**；
  `store`（门店）与 `channel`（渠道）是**组织/渠道**维度，单列一类，不算地区。
- **`/api/sources`（已物化）与 `/api/datasets`（已登记）** 保持**两个接口**，不合并：
  前者读 SQLite 物化库，后者是既有登记流程，语义不同（一个是"解析进来的表"，
  一个是"登记为周期性报表数据源"），合并会把两条已经能用的路搅在一起。
- **地区聚合走 HTTP**（`/api/sources/{id}/region/query`），**不**注册成 `tools.TOOLS`
  白名单条目：那要动 `COMPUTE_INTENTS` 和聊天能力清单，属范围外（要动就单独评审）。
- **口径细节（复用到的地方必须一致）**：物化入库**不做任何清洗**（脏数据原样进，
  为的是"入库的是原始事实"）；计算在 pandas 里做，且**按列形态分两支**：
  数据源自带金额列 → 直接按地区求和；只有 `Quantity × UnitPrice` → 套 D16 的
  `inclusive_day_window` 半开区间 + 取消单/退货/零价排除规则。**同一套口径，不分叉。**
- **遗留（明确记录，未做）**：① 地区维度没有"多级下钻"（省份→城市）联动；
  ② 「按国家」这个维度**没删**（只禁止它冒充地区），要删得单独评审；
  ③ 导入进度不是流式的（大文件时前端只有一个"正在导入"）；④ 单次导入的文件数上限
  是按体积/条目数硬限的，没有做并发导入。

## D24 · FR-007 响应路由解耦：**Intent → response_mode → 渲染**，非销售三类在销售工具之前结束分支（2026-09-29）

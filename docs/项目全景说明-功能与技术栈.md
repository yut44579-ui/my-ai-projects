## 0. 一句话定位

**一个把「每周手动做销售报表」变成「说一句就出报表」的本机系统，
核心原则是：LLM 只负责听懂人话和组织语言，所有数字必须由确定性代码算出来。**

链路固定为：

```
自然语言 → Intent（意图识别）→ 白名单 Tool（受限调用）→ 确定性计算 → Answer（代码排版 + LLM 只写解释）
```

**它是什么**：单机自用的**企业销售分析台**
**它不是什么**：不是 BI 平台（不出拖拽仪表盘）、不是多租户 SaaS、不是 text-to-SQL

## 2. 界面各部分功能

### 2.1 登录层（进入系统前）

| 部分 | 功能 | 实现要点 |
|---|---|---|
| **账号登录** | 账号 + 密码 + 图形验证码 → 进系统 | 密码用 pbkdf2 存**哈希**，绝不明文落盘 |
| **注册** | 账号 / 显示名（选填）/ 密码 / 确认密码 / 验证码 | 注册后**不直接进系统**，要管理员批准 |
| **游客登录** | 无需账号，随机分配「游客XXXXX」 | 只读浏览可用，受限功能处打 ⚠ 标记 |
| **管理员审批** | 「系统设置」里的账号管理：批准 / 拒绝 / 停用 / 删除 | 机器上**第一个注册的账号自动成为管理员** |
| **帮助 / 隐私抽屉** | 能问什么 / 数据从哪来 / 密码怎么存 / 会不会外发 | 登录卡片上不挂长句，细节收进抽屉 |

**四种「登不上」给四句不同的话**（这是刻意的设计）：
```
待批准     → 403「账号正在等待管理员批准」
未通过审批 → 403「该账号未通过审批」
已停用     → 403「该账号已停用」
密码错     → 401「账号或密码不对」     ← 只有这条是"你没通过校验"
```
顺序是**先验密码、再看状态** —— 否则「待批准」这句话就成了探测账号是否存在的探针。

### 2.2 业务台（登录后）

| 页面 | 功能 | 关键细节 |
|---|---|---|
| **首页** | 概览：交易行数 / 客户编号数 / 国家数 / 数据覆盖范围 | 三个数字都从当前数据源实时读出，换数据源跟着变 |
| **销售分析** | 维度（按日/按周/按国家）+ 指标（销售额/订单数/客户数/客单价）交叉表 | 可排序、分页、搜索、导出 Excel/CSV |
| **客户分析** | 客户级明细：客户号 / 销售额 / 订单数 / 购买次数 / 平均每单 / 首末购买 | 默认按销售额降序，可点表头改排 |
| **产品分析** | 商品级明细：货号 / 描述 / 销售额 / 数量 / 订单数 | 同上 |
| **异常发现** | 退货、取消单、异常值 | 两个退货口径分开报（负数量 / C 开头单），不混算 |
| **周报中心** | 一句话生成结构化周报（5 节）+ 导出 Word/Excel/Markdown | 周报 = 比较 + 趋势 + 结构 + 口径 + 结论，**不是第 6 个算法** |
| **原始数据** | 54 万行明细浏览（默认 50 条/页，不默认全塞） | 分页/排序/筛选全在后端算 |
| **数据管理** | 数据源列表 / 导入新数据源（Excel/CSV）/ 字段预览 | 导入**必须成为新 Dataset**，不与现有数据混 |
| **系统设置** | 运行状态 + 账号管理（仅管理员可见） | 显示数据源 SHA256 与登记时是否一致 |

## 6. 七个核心设计决策（面试重点）

### ★ 决策一：数字一律由代码算，LLM 一行数字都不许写

**为什么**：LLM 算数不可靠。行业实证是 Spider 2.0 基准显示真实企业 schema 上
text-to-SQL 准确率只有 **10.1%**。报表的全部价值就是数字准，这一条不能妥协。

**三道防线**（都真的在跑，不是设计）：
```
第一道  _BANNED_DIMENSIONS   在 LLM 之前拦掉数据里根本没有的维度
                             （问"华南区"→ 直接 unsupported，并点名"Country 不能当区域用"）
第二道  number_guard         回答里出现不在确定性结果集里的数字 → 整段作废
第三道  currency_guard       数据是人民币，模型写"英镑/£" → 整段作废
```

### ★ 决策二：冻结契约（Legacy Contract Freeze）

12 个端点的响应形状被冻结。**新能力只准走新文件 + 新路径**，老端点一个字不许动。
好处：前端、测试、审计链不会因为加功能而连环崩塌。
代价：加功能要开新文件（`api_chat.py` / `api_datasets.py` / `api_auth.py` 就是这么来的）。

### ★ 决策三：口径先定义，再计算（D16 清单）

最大风险不是「AI 理解错」，而是「**语义正确但口径算错**」：
下单日还是支付日？含不含退货？含不含取消单？含税吗？

所以有一份冻结清单，逐条写进 `app/engine/metrics.py` 的注释里：
```
时间字段   InvoiceDate（下单时间）
区间语义   含首尾全天：start 00:00:00 ~ end 23:59:59.999
取消单     排除 InvoiceNo 以 C 开头的行
负数量     排除 Quantity <= 0
负零单价   排除 UnitPrice <= 0
缺失客户   CustomerID 为空【不排除】（只影响客户维度），但要在报告里报空值行数
重复行     不去重，只报告重复行数（影响 0.421%，用户已拍板维持）
金额公式   sales_amount = sum(Quantity * UnitPrice)
```

### ★ 决策四：报告是「输出形态」，不是第 6 个 Intent（D20）

用户说「生成销售周报」时，做法不是新增一个 `weekly_report` 算法，
而是 **`sales_compare` + 四个既有工具的多段组合排版**。

否决新增算法的理由：
① 那等于**第二套口径**（同一个"本周销售额"有两个出处，早晚对不上）；
② Intent 数量会爆炸（月报、季报、年报各来一个）；
③ 周报的本质是**呈现**，不是新的计算。

**「本星期」这种相对说法不交给 LLM 翻译** —— 数据最后一天是周五，
模型多半会翻出半截周，拿 5 天比 7 天得出的"周环比"是假数字。

### ★ 决策五：排序状态机（`sort_source`）

表格排序最容易出的错不是"排不对"，而是"**我被系统悄悄改掉了**"。
所以引入一个显式状态 `sort_source = default | user`：

```
默认排序   按日/按周 → 按时间升序（★时间序列语义，不许改成指标降序）
           按国家    → 按当前指标降序
           客户/产品表 → 按销售额降序
Rule 2 切指标   default 态 → 排序交回调默认；user 态 → 【原样保留，不许覆盖】
Rule 3 切维度   → 清掉用户排序，回 default
Rule 4 点表头   → sort=该列，order 翻转，置 user
Rule 5 翻页     → dimension/metric/sort/order 完整保留（翻页不碰排序）
```
三层可见性：表头 ▲▼ + 一行文字「当前排序：订单数 ↓」+ 未排序列无标记。
（只做表头高亮不够 —— 实测过，用户根本看不见。）

### ★ 决策六：失败不产出错误文档

任一步失败 → 记录错误 + **不出文件**。否决"降级输出（部分数据/空值填充）"。
理由：**一份看起来正常但数字错的报表，比没有报表更危险。**

同理，越界查询（如问 2026 年的数据）后端**如实返回 0 条**，
不许自动截断区间、不许假装查的是有效范围。

### ★ 决策七：不用 Agent 框架 / 不用向量库

```
不用 LangChain/LlamaIndex/LangGraph
  → 流程是固定的几段（解析→确认→固化→执行），不是自主循环；
    框架会带来黑盒与依赖负担。"够用就不加框架"。
不用向量数据库（Chroma/FAISS/Milvus）
  → 需求是结构化字段映射（哪张表哪个字段），不是语义相似检索。
不用 ORM
  → 状态用 JSON 文件 + 进程内锁，单机自用够；换存储时 state.py 是唯一边界。
```

## 7. 优点（拿得出手的）

1. **数字可信是设计出来的，不是碰巧的**
   三层闸门 + 冻结口径 + SHA256 数据指纹 + LLM 零数字写入。这个组合在同类项目里少见。

2. **有真相来源**：54 万行真实数据、可核对的口径数字
   （2011年11月 = 1,509,496.33 元；某周 = 316,412.16 元，1913 行排除逻辑可逐条复算）

3. **验收不靠"我说我做了"**
   435 个 test 函数 / 537 个断言通过；CDP 真浏览器脚本（如排序 42/42、游客拦截 55/55）；
   独立 Oracle（用另一套 pandas 实现和 executor 对账，差 0.0）

4. **工程约束写死在代码里，不靠人记**
   `engine` 不许 import `ai`；`workers=1` 写进 `serve.py` 头注释；
   受保护视图/游客限制在执行处和入口两处都拦。

5. **决策可追溯**
   `DECISIONS.md` 21 条决策，每条都是「选了什么 / 否掉了谁 / 为什么」，
   连"某个决策是 Hermes 指令矛盾导致的"都如实记着。这是面试最值钱的部分。

6. **前端分层干净**：接口层 / 视图层 / 会话层 / 样式层分文件，
   没有掉进"2MB 单文件 index.html"的坑（旧项目教训已吸取）。

## 8. 缺点与风险（如实说，别掩盖）

| # | 问题 | 影响 | 现状/计划 |
|---|---|---|---|
| 1 | **没有 `requirements.txt`** | 换机器装不起来；依赖版本靠 venv 现状 | 已在 DECISIONS D18 记为待办，**仍未补** |
| 2 | **状态存储是 JSON + 进程内锁** | 只能单进程；两个 worker 会互相覆盖（表现为"执行记录少几条"） | 已用 `workers=1` 硬约束；换 MySQL 归 TASK-007 |
| 3 | **业务端点没有服务端权限校验** | "游客不能导入导出"是**前端拦的**（`session.js::guard()`），能绕过 | 已如实写进 D21，不吹成服务端鉴权 |
| 4 | **账号会话不是令牌** | 存内存、重启即失效、无签名、无权限范围 | 只用于账号管理三个端点，不参与业务端点 |

## 9. 面试怎么讲（建议话术骨架）

**问「你这个项目解决了什么问题」**
> 每周做销售报表要 1-2 小时：导数据、拉透视表、算指标、套格式，还容易算错。
> 我做了个系统，说一句「2011年11月卖了多少」直接给数，说一句「做份周报」直接出 Word。

**问「AI 在里面做什么」**（这题是分水岭）
> AI 只做两件事：**听懂人话**（把问题解析成结构化意图）和**组织语言**（写"为什么"和"建议"）。
> **它一个数字都不许写。** 因为它写的数字我无法验证，而报表的价值就是数字准。
> 具体是用三道防线拦的：意图阶段先拦掉数据里没有的维度；
> 答案阶段做数字闸门——回答里出现任何不在计算结果集里的数字，整段作废。

**问「为什么不用 LangChain / 为什么不上向量库」**
> 我这条链路是固定的四段，不是自主循环，框架只会变成黑盒和依赖负担。
> 向量库解决的是语义相似检索，我要的是结构化字段映射，用不上。

**问「怎么保证不出错」**
> 三个层面：① 口径先冻结成清单，逐条写进代码注释；
> ② 用第二套独立实现（另写的 pandas 代码）和主实现对数，差异 0.0；
> ③ 失败就不出文件 —— 一份看起来正常但数字错的报表，比没有报表更危险。

**问「遇到最难的 bug」**（选一个讲）
> 用户说"排序不对，127 排在 142 前面"。我一开始以为要把按日表改成按指标排。
> 后来做外部评审时被纠正了：按日表是**时间序列**，它就是该按时间排；
> 真正的 bug 是**用户看不出当前按什么排**，而且**手动排序会被切指标悄悄覆盖**。
> 最后是引入了一个显式状态 `sort_source = default|user` 才把语义钉死 ——
> 用户手动排过的顺序，任何自动动作都不许覆盖。

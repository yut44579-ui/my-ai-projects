# AI客服 · 决策记录

> 记判断和取舍，不记流水账。每条都要能回答"当时为什么这么定"。
> 格式：**决策 → 理由 → 放弃的方案及原因**。

---

## D1 「越用越聪明」主要不靠训练模型

**决策**：把"变聪明"拆成四层，训练只放最后。

```
① 知识层  没答上来的 → 待补充列表 → 人补一条 → 秒级生效
② 检索层  检索没命中的 → 补同义词/黑话 → 分钟级生效
③ 话术层  草稿被人改过 → 变风格示例 → 下次请求就生效
④ 模型层  微调 → 几小时到几天，且装不了事实
```

**理由**：
- ①②③ 贡献了"变聪明"的绝大部分，而且几乎不花钱不花时间
- 微调三条硬伤：**溯源不了**（答错了不知道从哪来的）、
  **删不干净**（知识过期要重训）、**权限会串**（训进去谁都能问出来）
- 每客户训一个模型 → 客单价撑不住，交付周期从 1 天变 1 周

**放弃的方案**："把公司资料喂给模型训练，它就知道公司的事了" ——
事实类知识用微调注入不可靠，且上面三条硬伤在客服场景是致命的。

## D2 ★ 没有验证的自我进化是放大器，不是进步

**决策**：每次学习都必须过评测集，确认准确率涨了才生效。

**理由**：人工随手改的一条草稿，如果直接当"标准答案"喂回去，
AI 会把那个人的临时口味学成规则 → **用的人越多，歪得越厉害**。

**落地**：`eval_case` 表 + `check_answer()`。
其中 `must_not_contain`（禁用词）是最重要的一类 ——
它专抓"答得挺像样，但说了不该说的"。

**放弃的方案**：让模型自评"这条答得好不好" ——
模型自评置信度非常不可靠，该说不知道的时候它也很自信。

## D3 检索质量拆成多个信号算，不让模型自评

**决策**：`quality = 0.70×top分 + 0.30×一二名分差`，再乘时效性惩罚。

**理由**：可靠的信号来自检索本身，不是模型的自我感觉。
- `top` — 命中够不够强
- `gap` — 一二名贴太近说明有歧义，不能自信
- `stale` — **过期内容混进来必须重罚**

**放弃的方案**：只用"最高相似度"当置信度。
那样知识库里同时有 2023 版和 2025 版时，两边分数都高 →
置信度很高 → **自动发出过期答案**。这是真实会发生的事故。

---

## D4 ★ 安全规则写在代码里，不写在提示词里

**决策**：报价/合同/退款/投诉/法律 **在调模型之前就拦**，直接转人工。

**理由**：
- 提示词是"请求"模型别说，代码是"保证"它说不了
- 模型会漏，而且漏的时候你看不出来 —— 它答得很通顺
- 提前拦还有第二个好处：**省掉一次模型调用**

**放弃的方案**：提示词里写"遇到报价问题请转人工"。
赌模型听话，代价太大。

## D5 平台强制的底线，不给客户开关

**决策**：可配的是语气/长度/覆盖范围/自动化程度；
**不可配**的是敏感信息拦截、审计日志、紧急停止开关、租户数据隔离。

**理由**：可配置 ≠ 什么都能配。
客户如果把"投诉"也设成自动发送，出事的是他的客户，但口碑是你的产品。

**做法**：用数据劝，不用"不允许" ——
"这类消息过去 30 天有 47 条，AI 答案有 31% 被人改过（平均只有 12%）。
你确定要自动发送吗？"

## D6 ★ 对客户不暴露内部岗位和姓名

**决策**：出站检查拦"财务/法务/主管/工号"这类内部身份信息。
**转人工就直接转，AI 不说话。**

**理由**（来自一次真实评审意见：「转人工就直接转，干嘛还要暴露职业名称跟岗位」）：
1. 等于把内部组织结构透给外部
2. 员工姓名泄漏后，客户下次会指名找他，人被绕过流程绑住
3. 说了"财务会处理"，万一是别人处理，客户会觉得被骗

**放弃的方案**：
- "已转人工 · 财务 李姐" —— 暴露岗位 + 姓名
- "我叫个同事帮你看下" —— 还是废话，见 D7

**保留**：内部员工之间不拦（同事知道是财务在处理，是正常且有用的信息）。

## D7 ★ AI 不解释自己的行为

**决策**：出站检查删掉所有以"我"开头的行为说明。

```
禁止：
  · "我叫个同事帮你看下"      ← 解释我要干什么
  · "我查了一下"              ← 解释我做了什么
  · "我给你走流程"            ← 承诺我会帮你
  · "已经为您转接"            ← 报告我的动作
```

**理由**（同样来自评审意见：「你人工就直接转就得了，还同事」）：
真人不这么说。真人只会 —— **会答就答，不会答就叫人来，不解释过程。**

★ 这条比"禁止客套话"更准：因为"我叫个同事"表面看不像客套，
但它和"亲，您好呢"是同一类病：**都在说 AI 自己，而不是在回答用户。**

**落地**：`SELF_NARRATION` 正则 + `_drop_sentences()`
（删**整句**而不是删词 —— 只删词会留下残句，比不删更糟）。

## D8 文档删除必须真的删

**决策**：`delete_document()` 同时删 doc 行和所有 chunk。

**理由**：只标记删除（软删）的话，旧内容会**永远留在索引里继续被回答**。
这类错误最隐蔽 —— 用户看到一个已经作废的规定，还以为是最新的。

**同时处理**：内容变了 → 先删旧 chunk 再重建。
不删的话新旧块会同时被检索到，模型可能拿到旧版本。

## D9 分层的降级顺序，免费模型不是默认兜底

**决策**：
```
主模型 → 同厂商便宜档 → ★ 不调模型直接给检索原文 → 只转人工
```

**理由**：
- **很多免费模型的条款允许用输入训练**，而这里的输入是公司内部资料
  和客户对话 —— 这是合规红线，比那点 API 费用严重得多
- 免费层普遍有限速和排队，客服场景等不起

★ 第三档（原文直出）是最容易被忽略但最实用的一层：
**零成本、零编造风险、用户至少拿到了信息**。
另两个项目里都已经验证过这个做法。

## D10 中文 2-gram + BM25，不引入向量库

**决策**：里程碑 1 用 2-gram + BM25，语义检索做成可插拔。

**理由**：
- 企业内部文本有大量未登录词（型号、缩写、内部黑话），通用分词器切不对
- 中小企业私有化部署的机器内存很小（2GB 是常态），
  sentence-transformers + torch 装上是 2GB+ 依赖，跑不动
- 几千到几万块的量级，SQLite 全表扫 + BM25 完全够

**代价**：处理"同义不同词"（咋弄/怎么办/怎么操作）弱。
用同义词表补一部分，剩下靠查询改写。

## D11 ★ 同义词只做"追加"，不做"替换"

**决策**：`expand_query()` 把标准说法**追加**到原查询后面。

**理由**：映射可能错（"打款"可能是付款也可能是收款）。
替换的话映射一错就彻底查不到；追加的话两种说法都能命中，
最坏情况只是多召回一点噪音。

**同时**：同义词**不自动生成**，只给候选让人确认（`missing_term_report`）。
口语→标准词的映射有歧义，自动猜错会让检索拉进不相关文档，
**比不命中更糟**。

---

## D12 待补充问题按归一化后合并计数

**决策**：`normalize_question()` 去标点去开头客套，再计数。

**理由**：客户问"报消单咋填"和"报销单怎么填"是同一件事。
不合并的话待补充列表会被同一类问题刷屏，管理员看不出重点。

**但只做轻量归一化** —— 做重了会把不同问题合并成一条，
反而更糟。宁可合并少了，不可合并错了。

## D13 失败原因必须分类记录

**决策**：`qa_log.failure_reason` 分六类，每类对应完全不同的修法。

```
no_hit          缺知识        → 补知识/补同义词
stale           缺时效        → 补日期或下架旧版
bad_style       缺风格示例    → 补风格
wrong_fact      事实约束不够  → 加固约束或改原文直出
should_escalate 判定错了      → 改转人工规则
banned          安全问题      → 补禁用表并查为什么没拦住
```

**理由**：不分清的话，"学习"就是瞎改 ——
缺知识的去改话术，永远修不好。
成功率只告诉你"好不好"，**原因分布才告诉你"该修哪里"**。

---

## D14 档位状态落库，不落进程内存

**决策**：降级/熔断的档位状态写数据库。

**理由**：单机时进程内变量更简单，但**多实例部署会失效** ——
A 机器已降级、B 机器还在打主模型，钱照样被烧。

**代价**：每次判定多一次读库。量级不大的话可以接受。
等真要高并发时，换成 Redis（但那是以后的取舍，不是现在的）。

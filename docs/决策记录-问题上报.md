# 问题上报（客服/销售 → 技术）

> 用户的原始需求：
> 「加一个远程提醒类似的功能，就是可以随时提醒技术开发人员报错、有 bug、需要去改
>   （这里最好是要填写问题、问题类型、具体错误原因等）。
>   因为使用这套系统的通常都是不怎么会用 AI 的小白销售或者客服，只会去回复话术。
>   点了这个就会有关于技术人员专门处理这些问题的界面。
>   开发人员专门在这里处理问题，最后提交问题，提交完之后客服或者销售这里的能够知道
>   —— 就这种设计逻辑。」

---

## D84 ★★★ 报问题的人**不需要懂技术**，这是这个模块唯一的设计原则

**小白客服面对一条 AI 答错的回答，他能提供的信息只有**：
> "这答得不对。"

**就这样。没有别的了。**

**所以如果表单要求他填"复现步骤""错误堆栈""请求参数"**：
```
他不会填 → 这个问题永远不会被上报
→ 然后他会在微信里私聊技术，或者干脆不管了
→ 整套上报机制形同虚设
```

### 分工

```
他填的（2 个必填）
  · 哪儿不对      → 下拉选，用大白话（答错了 / 答不上来 / 点了没反应 / 太慢 /
                    说了不该说的 / 格式不对 / 不会用 / 其他）
  · 一句话说清楚   → 输入框

系统自动抓的（他一个字都不用管）
  · 那一句问答的完整记录：AI 判成了哪一档、为什么、检索质量、
    耗时、token 数、原始问题、**改写后的检索词**
  · ★ 命中了哪些资料、每条的**相关度分数**
    —— 技术最需要看的就是这个：是"根本没检索到"还是"检索到了但答错了"
  · 这个用户前后的几轮对话（一条问答看不出上下文）
  · 最近的服务端报错
```

**界面上明确写出来**（`#isAttach`）：
> ✅ 系统会自动附上：这条问答的完整记录（AI 判成了哪一档、检索质量、
> 命中了哪些资料）、这个用户最近的几轮对话、以及最近的服务端报错。

**★ 为什么要显式告诉他**：他才知道自己**不用去翻日志、不用截图**。
不写这句的话，他第一反应还是"我该去哪儿找日志"。

### 入口就在现场

```
实时页每条问答旁边 → 「⚠ 这条不对」  ← 就地就能报，不用记是哪一句
人工页            → 「⚠ 报个问题」   ← 带上这个用户的 id 和问题
右下角常驻浮动按钮 → 「⚠ 报个问题」   ← 哪儿都能点
```

**★ 这个设计的价值**：客服看到不对的**当口**就能报，
不用"先记住、再去别的地方、再描述" —— 那个链路太长，中间一定丢。

## D85 ★★★ 闭环必须由**报的人**确认，不能由技术自己宣布修好了

**状态机**：
```
new（待处理）
  → working（处理中，技术点了"我来处理"）
      → resolved（技术提交了解决方案，**但这不是结束**）
          → closed（报的人点"好了"）
          → working（报的人点"还没好" —— 打回，带他的补充说明）
```

**★ 为什么非要报的人点头**：
> 技术说"修好了"、但他改的地方和用户遇到的问题**不是一回事** —— 这种事极其常见。
> 报的人不点头，这个问题就不算完。

**实测（走公网）**：
```
提交方案    → {"new":1, "resolved":1, "wait_ack":1}
说"还没好"  → {"new":1, "working":1, "resolved":0}    ← 打回，带上补充说明
说"好了"    → {"resolved":0}                          ← 真的关闭
```

**★ 还有一条：技术说"不是问题"也必须写理由**。
```python
def reject(issue_id, *, reason, ...)   # reason 是必填
```
不然报的人会觉得"我的问题被无视了"，**下次就不报了**。
> 让人愿意继续报问题，比这一次的判定更重要。

## D86 ★★ HTML 属性里的引号冲突：按钮看起来正常，但点了没反应

**现象**：「这条不对」按钮渲染出来了、样式也对，**但点了毫无反应**。

**原因**：
```html
onclick="openReport(64, "web-rg9vaxk6", "打样要多久")"
                    ↑ JSON.stringify 产生的是**双引号**
                      而 onclick 属性也是双引号界定的
→ 属性在第一个双引号处就被截断了，剩下的变成散落的假属性
```

**★ 这个 bug 特别难看出来**，因为：
```
· HTML 不报错（浏览器会尽量宽容地解析）
· 页面看起来完全正常（按钮在那儿，样式也对）
· 只有"点了没反应"这一个症状
→ 会让人以为是函数没绑定、或者事件没冒泡，往错的方向查
```

**修法**：整个 `onclick` 用**单引号**界定，内部的 JSON 双引号就不冲突了。

## D87 ★★★ `let` 的声明位置会影响运行（暂时性死区）

**现象**：「问题」页打开是一片空白，控制台里 `ilistHtml` 显示
`Cannot access 'iFilter' before initialization`。

**原因**：
```js
switchTab(location.hash)   // ← 脚本顶层，立即执行
   → loadIssues()          // ← 读 iFilter
       ...
let iFilter = 'open'       // ← 声明在 300 行之后
```

**★ `let`/`const` 有暂时性死区（TDZ）**，不像 `var`：
```
var  → 提升并初始化为 undefined，提前访问只是拿到 undefined
let  → 提升但**不初始化**，提前访问直接抛 ReferenceError
```

**修法**：所有跨函数共享的状态**统一在脚本开头声明**。

**★ 教训**：
> "按功能就近声明变量"这个习惯，在有**顶层立即调用**的脚本里会出问题。
> 而且它只在"启动时正好落在那个 hash"时才暴露 ——
> 我一开始没发现，是因为我每次都从别的标签页切过去（那时脚本早就执行完了）。

## D88 ★ 竞态：详情刚插进去就被列表重绘冲掉了

**现象**：点问题列表，详情加载不出来。

**原因**：
```js
async function openIssue(id) {
  iCur = { id };
  loadIssues();          // ← 异步，会整个重写 #ilist
  const d = await api(...);   // ← 等数据
  ...insertAdjacentHTML('#ilist', 详情)   // ← 插进去
  // 但 loadIssues() 可能**这时候才返回**，把详情冲掉
}
```

**修法**：**把顺序固定下来** ——
先 `await` 数据、再 `await loadIssues()`、最后插详情。

> 这类"谁后写谁赢"的竞态，修法永远是**固定顺序**，不是加延时。

## 这一轮的状态

```
线上  服务 active
      报事侧：提交成功，自动附上「完整问答 + 2 轮对话 + 命中的 2 条资料」
      处理侧：能看到改写后的检索词、相关度分数、判定依据、耗时、tokens
      闭环：待处理 → 处理中 → 已解决（等确认）→ 已关闭 / 打回
      报的人：能看自己报的每一条处理到哪一步
      手机：溢出 0px
```

```
实时 │ 试一句 │ 人工 ⑮ │ 问题 ① │ 知识库 │ 渠道 │ 模型 │ 学习 │ 治理
```
「问题」标签带红色角标，有活的时候会亮。

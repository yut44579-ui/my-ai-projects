## D108 ★★ 作品集最坑的两个"不是 bug 的 bug"

### 坑① 我插错了数组

```
data.js 里有**两个数组**：window.PROJECTS 和 window.PRESET_QA
我用 t.rfind("];") 找数组结尾 → 拿到的是最后一个（PRESET_QA 的）
→ 项目被插进了问答区
★ 语法还是对的（数组里多一个元素，合法），只有"项目数还是 2"能看出来。
```

**★ 教训**：
> **"改完要验证结果"，不是"改完看脚本报没报错"。**
> 这个错如果不是我顺手 eval 了一下数数组长度，会一直到线上才发现。

**修法**：从 `window.PROJECTS = [` 的位置往后找**第一个** `\n];`。

### 坑② nginx 给 .js 设了 7 天缓存

```
服务器上 /var/www/portfolio/assets/data.js 里明明有 3 个项目，
curl 带 ?v=随机数 拿到的也是 3 个 —— 只有"浏览器缓存"那一层是旧的。
表现：首页还是 2 张卡片、详情页全空（连标题都是占位符 …）
```

**★ 为什么这个坑特别难查**：
```
· 它不是服务端问题 —— 文件是新的
· 它也不是代码问题 —— 代码是对的
· 它只在"浏览器已经访问过旧版"时出现 —— 而我自己刷新时用的是同一个 profile
→ 排查时极容易往"文件没传上去"的方向走
```

**修法**：缓存按"内容会不会变"分开
```
html / js / css   →  no-cache, must-revalidate
                     （每次都问服务端，没变就 304，几乎无成本）
图片 / 字体        →  1 天
                     ★ 不给 7 天 —— 作品集的截图会用**同样的文件名重拍**
```

**★ 这条对任何"会持续更新"的站点都是通用的**：
> 把 JS/CSS 设长缓存，等于**每次部署都要等缓存过期**，
> 或者被迫给每个文件加版本号。对一个个人作品集来说，
> `no-cache + ETag` 是性价比最高的方案 —— 304 几乎不耗流量，
> 而"改完立刻生效"这件事值这个成本。

**验证时也要注意**：测部署结果要用**全新的浏览器 profile**
（或者 `Network.setCacheDisabled`），否则你测的是自己的缓存。

## D109 ★ 模板的兜底文案会误导

详情页的演示区有句兜底：`演示账号写在登录页上。`

```
这句话是给"有登录"的系统准备的（AI供应链、销售 Agent 都有）
但 AI客服**根本不用登录** —— 套上去等于告诉访客去找一个不存在的东西
```

**修法**：加一个可覆盖的 `demo.publicNote` 字段，优先级：
```
publicNote（项目自己写） > publicAccount（给个账号） > 兜底
```

**★ 教训**：
> **兜底文案只对"符合它假设"的对象成立。**
> 加新对象（新项目、新渠道、新类型）时，
> 要检查一遍"现有的兜底是不是还成立"，而不是等它显示错了才发现。

## D110 顺手补上一个真缺陷：深链接不工作

做截图脚本时发现的（不是作品集的问题，是 AI客服 自己的）：

```
只改地址栏的 # 不会重新加载页面，
而初始标签是靠"加载时读一次 hash"决定的
→ 手动把 #live 改成 #ho 没反应
→ 别人分享一个 #issue 的链接给你，点了也不跳
```

**修法**：加 `hashchange` 监听。
★ 注意 `switchTab` 内部用的是 `history.replaceState`（不触发 hashchange），
所以不会自己套自己。

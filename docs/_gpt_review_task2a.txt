BLOCKER-2：rows_excluded / excluded_amount 在关闭规则时的语义没有完全定义

你已经定义了：

例如：

cancelled 是否 0？已经规定是

multi_rule_hit 是 0 还是 1？

rows_excluded 是 1 还是其他？

excluded_amount 是否包含它？应该包含，因为它最终仍被排除。

尤其是 multi_rule_hit，当前定义：

如果不写死，Claude 很容易出现两种实现。

建议直接补成
统计规则均以“当前启用的 exclude_* 规则”为准：

- rows_excluded：至少命中一条“已启用排除规则”的去重行数
- excluded_detail：仅统计已启用规则；关闭规则对应键固定为 0
- multi_rule_hit：同时命中 ≥2 条“已启用排除规则”的去重行数
- excluded_amount：最终因已启用规则被排除的行的 Quantity*UnitPrice 之和

这样关闭规则的反向校验才真正具有确定语义。

二、强烈建议修改的 3 个问题
1. end ... 23:59:59.999 建议不要用“最后一毫秒”实现

你目前写的是：

end 补位为当天 23:59:59.999

这本身是可以实现的，但 Excel/Pandas 的 datetime64[ns] 实际精度高于毫秒。

因此严格来说：

2011-11-27 23:59:59.999500

是否属于当天？

按照“23:59:59.999”字面定义，它不属于。

但业务上的“含首尾全天”通常更稳妥的实现是：

InvoiceDate >= start 00:00:00
AND InvoiceDate < end + 1 day

也就是：

[2011-11-21 00:00:00, 2011-11-28 00:00:00)

这才能真正表达“含 27 日全天”。

**但是注意：**你已经把 D16 固化成 23:59:59.999，所以不能让 Claude 自己改口径。

建议在 D16/TASK 中明确：

实现允许使用等价的半开区间：
InvoiceDate >= start_datetime
AND InvoiceDate < end_date + 1 day

其业务语义必须等价于：
start 00:00:00 ~ end 23:59:59.999

否则不要让 Claude 自行发挥。

2. “完全重复行数”的定义还不够精确

现在写：

duplicate_rows = 完全重复行数

问题是 pandas：

Python
运行
df.duplicated().sum()

统计的是重复出现的后续行数量，不是“重复组涉及的总行数”。

例如：

A
A
A

duplicated().sum() = 2。

但有人可能理解成：

完全重复的行数量 = 3

这会影响测试。

建议明确：

duplicate_rows：
采用 pandas duplicated(keep="first").sum() 语义，
即每个完全重复组保留首次出现行，其余重复出现行计数。
本 TASK 不删除这些行。

这样 Oracle 和 executor 可以严格一致。

3. AC-04 的“所有行纳入”措辞有歧义

目前：

容易被 Claude 理解成：

但实际显然不是：

    ↓

所以建议改成：

rows_in_range 必须等于该时间区间内原始行数。
随后再独立应用排除规则。

这个非常重要。

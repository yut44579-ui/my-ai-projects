## D113 ★★★ 护栏本身成了密钥的藏身处

**准备上传时全项目搜密钥，抓到两处 —— 在我自己的护栏测试里：**

```python
# scripts/smoke9.py（"不许出现密钥"的检查表）
SECRETS = [
    (r"sk-[A-Za-z0-9]{16,}", "厂商 API Key"),
    (r"<服务器 SSH 口令>", "服务器 SSH 口令"),   # ← ★ 原文这里是真实口令，此处已脱敏
    (r"<数据库真实口令>", "数据库真实口令"),       # ← ★ 已脱敏
]
```

**★★ 这个错误比"忘了 gitignore .env"更隐蔽**：
```
· .env 被 gitignore 是常识，容易想到
· 但"检查密钥的清单"看起来是在**防**密钥，
  没人会怀疑它本身就是密钥
· 而且它藏在一个 `scripts/smoke9.py` 里 ——
  一个"护栏测试"，代码审查时最容易被跳过的那类文件
```

**修法**：真实值挪到 **`.forbidden`（被 gitignore）**，测试运行时读：
```python
_FORBIDDEN_FILE = ROOT / ".forbidden"
if _FORBIDDEN_FILE.exists():
    ...载入...
else:
    print("⚠ 没有 .forbidden —— 跳过「本机口令」这两条检查")
    print("  （这是**有意的**：具体口令不该写进仓库）")
```

**★★ 注意这里的设计取舍**：
```
读不到时**跳过检查并打印警告**，而不是硬编码一份进仓库
→ 代价：别人 clone 下来跑，那两条检查是跳过的
→ 收益：仓库里永远不会出现真实口令
★ 这个取舍是明确选的：**"检查不完整"比"密钥泄露"轻得多**。
```

**★ 诚实说明局限**：`.forbidden` 是明文本地文件，不是密钥管理系统。
它只解决"不要把密钥提交进仓库"这一个问题。

## D114 ★★ 提交前必须 verify 的是"会提交什么"，不是"我加了 gitignore"

**实际做的检查**（不是假设）：
```
① git add -A 之后，先看将提交的文件列表
   → 137 个文件，检查有没有 .env / .forbidden / *.db / .venv / __pycache__
② git ls-files 再确认一次（暂存之后、提交之前）
③ 提交之后、推送之前，扫一遍**所有将被推送的文件内容**
   → 找 sk-… / 服务器口令 / 数据库口令
④ 推送前再看一遍远端将要更新的清单
```

**★ 为什么是四道而不是一道**：
```
· .gitignore 写了不等于生效（路径写错、大小写、已被 add 过的文件）
· 暂存区干净不等于内容干净（.env.example 这类文件里可能有真值）
· 本地干净不等于远端干净（之前推过的东西还在历史里）
```

## D115 中文文件名让我的检查脚本误报

**现象**：检查"决策文档在不在仓库里"时，显示 **0 份**。

**原因**：
```
git ls-tree 默认 core.quotepath=true，
中文文件名被转义成八进制：
  "docs/\345\206\263\347\255\226\350\256\260\345\275\225.md"
→ 我的 PowerShell 过滤 `-like "ai-customer-service/docs/*"` 匹配不上
  （行首是引号）
```

**★ 但它长得非常像"文件真的没进去"** —— 我差点去重新提交一遍。

**修法**：`git -c core.quotepath=false ls-tree ...`

★ 教训：**检查脚本报"没有"时，先确认检查方法本身对不对**，
  尤其是涉及非 ASCII 文件名 / 编码 / 路径分隔符的时候。
  这和之前"补丁没生效但脚本报成功"是同一类问题，方向相反。

## D116 提交作者邮箱不一致

**现象**：仓库里 71 次提交用的是
`251756466+yut44579-ui@users.noreply.github.com`，
我新加的 3 次用了仓库级配置里的占位符 `tyu821882@example.com`。

**修法**：
```
① 先把仓库级 user.email 改对（以后不会再错）
② git filter-branch 只改这 3 次的作者/提交者邮箱（作者日期保留）
③ 先建备份分支，force-with-lease 推送，推完删掉备份分支
```

**★ 顺带做的事（重要）**：强制推送**之前**又扫了一遍密钥 ——
因为 force push 会把新历史覆盖上去，这时候再发现问题就晚了。

## D118 ★★★ 事故复盘：口令进过公开仓库

**先说结论**：
```
· 仓库现在的 HEAD（main）是干净的 —— 所有提交的历史里都没有口令
· ★ 但**旧提交在 GitHub 上按 SHA 仍然可读**（已实测确认 HTTP 200，内容完整）
  → 因为 Git 的删除只是"不再引用"，对象要等 GitHub 自己 GC
  → 在这之前，知道 SHA 的人仍然能取到
· ★ 所以**唯一真正的处置是轮换口令**，而不是指望它没被看到
```

### 事情是怎么发生的（三个错，一个比一个隐蔽）

**错① 护栏测试里写着真实口令**
```
scripts/smoke9.py 是"不许出现密钥"的检查表 ——
它必须知道口令是什么才能检查，于是把真实值写进了代码。
★ 这比忘记 gitignore .env 更隐蔽：它看起来在**防**密钥。
→ 修法：真实值挪到 .forbidden（gitignore），读不到就跳过并警告
```

**错② 写复盘文档时，又把口令原样引用了一遍**
```
为了展示"错①那段代码长什么样"，我在决策记录里把它**原样贴了出来**。
★ 原因和错①一样：我以为"文档不算代码"。
★ 讽刺的是，这份文档的正文里刚写完"护栏本身成了密钥藏身处"。
→ 修法：脱敏成 <服务器 SSH 口令> / <数据库真实口令>
```

**错③ 第一次清理历史时，回退步数数错了**
```
含口令的提交：950491f
我 reset --soft HEAD~1 → 退到了……950491f **本身**（应该退 2 个）
→ 新提交的 parent 就是含口令的那个提交 → 口令还在历史里
★ 而我当时**以为已经清干净了**（因为新建的那个提交是脱敏内容）
→ 是"扫全历史"这个检查抓出来的
```

### ★ 三条可复用的纪律

**① 密钥扫描要扫"全部会被提交/推送的文件"，不分类型**
```
代码 · 文档 · README · 决策记录 · 测试用例 · 提交信息本身
★ "文档不算代码"是错的 —— 密钥不分文件类型。
```

**② 改历史之后，必须扫"全历史"，不能只看 HEAD**
```
错误示范：git grep <口令> HEAD          → 干净（但历史里还有）
正确做法：for sha in $(git rev-list --all); do git grep <口令> $sha; done
★ 我是靠这条才发现错③的。
```

**③ "删掉"不等于"抹掉"**
```
· 本地：删分支 + reflog expire + gc --prune=now
· 远端：force push 覆盖引用
· ★ 但远端对象仍可能按 SHA 可读，直到对方 GC
· ★ 真正的处置是**轮换凭据** —— 假定它已经泄露
  （不是"应该没事吧"，是"假设它被看到了"）
```

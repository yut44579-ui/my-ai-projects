【总体判断】有条件认可

本轮修订方向正确，而且比上一版更贴近“可交付产品”而不是纯后端验证。核心调整应是：不要把“前端优先”理解成先做一个独立前端 Demo，而是改成“最小垂直切片优先”。

当前方案有 3 个主要风险：

TASK-002 偏大，且把 Spec、数据加载、执行、渲染一次塞进去，AI Agent 连续执行时容易出现“每个文件都写了，但整体链路没真正跑通”。

TASK-004 虽然定义了真功能，但排在 TASK-005 后面没问题，不能排在后端闭环之前；应该提前做一个极小前端切片。

自动连续执行场景下，不能只依赖 pytest。必须增加“任务级验收门禁 + 真文件 E2E + 前端可操作性检查 + 失败停止”。

【顺序建议】前端优先怎么落地才不是 Demo

建议把当前：

TASK-002 → TASK-003 → TASK-004

改成：

垂直切片 A → 垂直切片 B → 横向完善

第一刀：最小真闭环

只实现：

真实 Excel 上传 → 固定指标“上周销售额” → 计算 → 真 Excel → 下载

但这里的“前端”也必须参与：

浏览器
 ↓
上传 Excel
 ↓
FastAPI /api/upload
 ↓
pandas 读取
 ↓
固定 Report Spec
 ↓
executor
 ↓
openpyxl 生成 Excel
 ↓
浏览器下载

页面只需要有：

上传文件

文件状态

“生成报表”按钮

执行状态

结果数字

下载 Excel

错误信息

这不是 Demo，因为每一个按钮都经过真实 API，并产生真实文件。

第二刀：加入 Spec

在第一刀跑通以后增加：

一句话：
“生成上周销售额报表”
        ↓
/api/parse
        ↓
Report Spec
        ↓
前端可读展示
        ↓
用户确认
        ↓
/api/execute

此时才开始接 AI Parser。

第三刀：横向补齐

再逐步加入：

数据字典

多指标

任务列表

执行记录

Evaluation Harness

定时

审计

所以我建议把“前端优先”重新定义成：

UI 优先验证，但以垂直业务闭环为单位，而不是 UI 与后端分离开发。

这是本轮最应该修改的地方。

【拆解建议】TASK-002 是否过大、怎么拆

是，TASK-002 对 Claude Code 来说偏大。

尤其：

spec/models.py
metrics.yaml
loader.py

实际上包含了 Spec 建模、数据读取、Schema 推断、业务计算、Excel 输出、测试 六个不同责任。

建议拆成：

TASK-002A：最小数据执行核心

只负责：

loader
 ↓
schema
 ↓

数值结果

验收：

pytest

并且：

“上周销售额”必须与独立 pandas 基准计算完全一致。

不要在这里做 Excel 渲染。

TASK-002B：Report Spec + Renderer

负责：

Report Spec
metrics.yaml

executor

openpyxl

真实 Excel

验收：

Spec 可以序列化/反序列化

固定 Spec 可以执行

输出 Excel 存在

Excel 能被重新读取

关键结果与基准值一致

TASK-002C：最小 API 垂直切片

把：

/schema
/spec
/execute

真正串起来。

然后马上做一个极简前端。

【前端形态建议】页面结构 / 技术形态

页面：建议单页，不建议四个独立页面

当前阶段我建议：

┌─────────────────────────────────────┐
│ Sales Report Agent                 │
├─────────────────────────────────────┤
│ ① 数据                              │
│ [上传 Excel]  文件.xlsx ✓           │
│                                     │
│ ② 建立任务                          │
│ [ 生成上周销售额报表              ] │
│                                     │
│ ③ Report Spec                       │
│ ┌─────────────────────────────────┐ │
│ │ 指标：销售额                    │ │
│ │ 时间：上周                      │ │
│ │ 时间字段：order_date            │ │
│ │ 排除条件：...                   │ │
│ └─────────────────────────────────┘ │
│              [确认并执行]           │
│                                     │
│ ④ 执行结果                          │
│ 销售额：¥ xxx                       │
│ 状态：执行成功 ✓                   │
│ [下载 Excel]                        │
│                                     │
│ ⑤ 执行记录                          │
│ 任务 / 时间 / 状态 / 下载           │
└─────────────────────────────────────┘

这比四个页面更适合 MVP。

因为用户的真实操作本质上是一个流水线：

数据 → 指令 → 确认 → 执行 → 结果

可以在视觉上分成 5 个区块，但不需要真的做 5 个路由/页面。

技术形态

当前阶段：

原生 HTML + CSS + JS 分文件完全够。

建议：

web/
├── index.html
├── app.js
├── api.js
├── style.css
└── components/
    ├── upload.js
    ├── spec.js
    ├── execution.js
    └── history.js

甚至第一阶段可以暂时不拆 components/。

真正重要的是：

UI
 ↓
api.js
 ↓
FastAPI

而不是有没有 Vue。

现在为了“看起来像正式产品”而引入 Vue/React，反而会增加 Agent 工作面。

等功能稳定后，如果前端复杂度真的增长，再迁移框架。

【必须的保护机制】自动执行场景下的门禁

必须有，而且我认为这是本轮比“前端框架选择”更重要的事情。

每个 TASK 不应该是：

Claude Code：代码写完了
→ 下一个 TASK

而应该是：

实现
 ↓
静态检查
 ↓
单元测试
 ↓
API 测试
 ↓
真实文件测试
 ↓
验收条件
 ↓
PASS → 下一任务
FAIL → 停止
最低门禁

每个 TASK 至少：

1. pytest
2. Python import / syntax check
3. FastAPI endpoint smoke test
4. 真实 Excel 输入
5. 真实 Excel 输出重新读取
6. git diff 检查

对于前端 TASK 再增加：

7. 页面实际打开
8. 点击上传
9. 点击执行
10. 确认结果
11. 下载文件
更重要：失败必须停止

不要允许：

TASK-002 FAIL
       ↓
Claude 猜测问题
       ↓
继续 TASK-003
       ↓
TASK-004
       ↓
最后发现整个链路坏了

应该：

TASK N
 ↓
验收
 ├─ PASS → TASK N+1
 └─ FAIL → STOP

而且每个 TASK 最好预先写死：

Acceptance Criteria

而不是让 Agent 自己判断“应该算完成”。

再增加一个保护

禁止 Agent 在测试失败时修改测试来让测试通过。

测试属于验收基准，不属于实现目标。

【最容易翻车的地方】

1. “真前端”最后变成半真半假

最危险的代码是：

JavaScript
const mockResult = {...}

或者：

JavaScript
setTimeout(() => {
    showSuccess()
}, 1000)

MVP 阶段应该明确禁止：

mock API

假任务

假执行状态

假 Excel 下载

TODO 按钮

静态统计数字

所有核心按钮必须调用真实 API。

2. Excel Schema 假设过早固化

“上周销售额”看似简单，实际上至少涉及：

销售额字段叫什么？

日期字段叫什么？

日期格式？

时区？

上周定义？

是否包含退款？

空值怎么办？

重复订单怎么办？

因此第一条垂直切片应该明确：

只支持一份预定义测试 Excel Schema。

不要在 MVP 第一刀就试图解决“任意 Excel”。

3. AI Parser 做得太早

不要让：

自然语言
 ↓
LLM
 ↓
复杂 Spec
 ↓
执行

成为第一条 E2E 链路。

第一条链路应该：

固定 Spec
 ↓
确定性执行

然后：

自然语言
 ↓
AI Parser
 ↓
固定/受限 Spec
 ↓
确定性执行

这样出了问题才能知道究竟是：

AI 理解错

Spec 错

Executor 错

Excel 错

4. “能生成 Excel”不等于“报表正确”

必须保留独立 Oracle：

测试 Excel
   ├── Agent Executor → 结果 A
   └── 独立 pandas → 结果 B

A == B

这个机制应该成为整个项目的核心质量保障之一。

5. Agent 连续开发导致范围漂移

尤其 Claude Code 很容易出现：

“既然已经做到这里，我顺便把 XXX 重构一下……”

然后一个 TASK 变成几十个文件。

建议每个 TASK 明确：

允许修改：
app/engine/*
tests/test_executor.py

禁止修改：
前端
数据库
部署
其他模块

必要时再加：

超出任务范围发现问题，只记录，不自行扩展。

【必须修改的项】

P0

把 TASK-002 拆成 002A / 002B / 002C。

新增“最小真垂直切片”作为前端启动点。

第一条 E2E 固定为：

真实 Excel → 固定 Spec → 确定性计算 → 真 Excel → 浏览器下载。

所有 TASK 增加明确 Acceptance Criteria。

建立：

PASS → 下一 TASK；FAIL → 停止
的自动门禁。

禁止核心前端功能使用 mock 数据/假 API/假下载。

保留独立 pandas Oracle，不能让 executor 自己证明自己正确。

P1

前端暂时采用单页多区块 + 原生 HTML/CSS/JS 分文件，暂不引入 Vue/React。

TASK-005 AI Parser 放在确定性执行闭环之后。

第一版 Excel 明确限定 Schema，不要试图支持任意 Excel。

增加真实文件重新读取验证，而不是只检查 HTTP 200。

增加前端失败状态：上传失败、解析失败、Spec 无法确认、执行失败、下载失败都必须可见。

最终建议顺序：

    ↓

    ↓
TASK-002C API 最小闭环
    ↓
TASK-004A ★ 真前端最小垂直切片
    ↓
     【真实 Excel → 真实报表】
    ↓
TASK-003/004B API + 前端补齐
    ↓
TASK-005 AI Parser
    ↓
TASK-006 Evaluation Harness
    ↓
TASK-007 定时 + 审计

**核心判断只有一句：这轮不要做“前端 Demo 优先”，而要做“可操作的最小产品闭环优先”。**这样既满足“先看到真正能用的前端”，又不会牺牲上一轮确定的确定性执行、Report Spec 和可审计性。

3. CustomerID 空值：这是 TASK-006 的核心口径问题

你这里千万不要把空 CustomerID 当成一个“匿名客户”。

目前：

总行数：541,909
CustomerID 为空：19,113

空值比例约：

3.53%

但这里真正重要的不是 3.53%，而是：

这 19,113 行对应多少销售金额？

因为你已经发现大额订单可能集中在那里。

所以我建议：

客户分析统一采用：

客户维度指标仅覆盖 CustomerID 非空记录。

销售总额则继续遵循现有口径：

CustomerID 为空的记录仍计入销售额，但不计入客户数及客户维度分析。

这是非常干净的边界。

更进一步：不要让用户自己猜覆盖范围

客户分析结果最好自动带：

JSON
{
  "customer_scope": {
    "rows_with_customer_id": 522796,
    "rows_without_customer_id": 19113,
    "sales_amount_all": "...",
    "sales_amount_customer_scope": "...",
    "customer_scope_sales_share": "..."
  }
}

这样系统可以回答：

本次客户分析覆盖有 CustomerID 的成交记录，占全部销售额 XX%。

这个 XX% 必须代码计算。

不要让 LLM计算。

还有一个非常重要的边界

不能说：

新客 1,234 人。

然后让用户理解成“真实业务历史上的新客”。

因为数据集从：

2010-12-01

才开始。

所以应该叫：

数据集内新客

定义：

CustomerID 非空
且该客户在整个数据集中的首次有效购买日期落在目标区间

而不是：

这个客户人生第一次购买。

这是 TASK-006 必须写入 AC 的。

4. “复购”必须先把定义锁死

这是另一个很容易产生争议的地方。

建议：

购买次数

定义为：

CustomerID + distinct InvoiceNo

而不是：

行数

否则一个订单包含 20 个商品行，会被误认为购买 20 次。

复购客户

例如：

purchase_count >= 2

则：

repeat_customer = true
复购率

建议定义：

复购客户数 / 目标客户总数

但必须把“目标客户”写死：

目标期间内至少有一次有效购买的 CustomerID 非空客户

否则：

复购率 32%

这个数字实际上没有可复核意义。

5. “沉睡/流失”：只做沉睡，不做流失预测

这是我明确建议修改的地方。

不要叫：

流失客户

因为“流失”很容易被理解成预测结论。

改成：

沉睡客户 / 长期未购买客户

定义成规则：

reference_date - last_purchase_date >= inactivity_days

例如：

inactivity_days = 90

完全确定性。

不要做：
客户 A 流失概率 87%

也不要：

预测未来 30 天不会购买

这就进入 ML / 统计预测了。

当前项目没必要。

6. RFM 能不能做？
能做，但我建议 TASK-006 不做 RFM 分群。

因为 RFM 本身并不违反你的铁律。

可以确定性计算：

R = reference_date - last_purchase_date
F = distinct InvoiceNo count
M = sales amount

完全可以复现。

问题是后面的：

R=5 → 5分
F=23 → 4分
M=50000 → 5分

到底怎么分？

你需要定义：

分位数还是固定阈值？

5 档还是 10 档？

并列值怎么处理？

reference date 是数据最大日期还是用户查询结束日？

负销售如何处理？

CustomerID 空值怎么处理？

这些都不是技术难题，但会明显增加口径复杂度和测试量。

所以：

RFM v1 暂缓，不是因为不能确定性算，而是因为当前阶段收益不足以抵消口径复杂度。

以后如果做，建议先做：

R / F / M 原始指标

再固定规则分箱。

不要让 LLM 动态决定分群。

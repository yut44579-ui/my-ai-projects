3. 归因分析最大的风险，以及怎么保证 LLM 碰不到数字

这是 TASK-005 最重要的架构要求。

你的思路是对的，但我建议再推进一步：

不仅数字不能由 LLM 判断，“主要是 X 和 Y”也不要让 LLM 决定。

因为：

哪个国家贡献最大？

本质上已经是一个排序/判断问题。

既然代码完全可以确定：

Python
运行
sorted(contributions, key=abs(delta), reverse=True)

就没必要让 LLM 再做一次。

推荐的数据流
Step 1：代码计算

假设：

上期 Country 销售额

delta = current - previous

}

然后代码排序。

Step 2：代码决定“主要贡献者”

negative_contributors_top_n = 3

或者：

取 Top 3

      "dimension": "Country",

Step 4：最好连“主要”都代码生成

更严格的设计是：

【解释/措辞】
LLM 生成

LLM：

这样你的安全边界就非常漂亮：

LLM 不负责事实判断，只负责事实的语言表达。

4. 还有一个非常重要的归因数学约束

必须加入一个 AC：

贡献和必须能够解释总变化

对于同一指标：

Total Δ = Current Total - Previous Total

对于所有维度：

Σ Dimension Δ = Total Δ

允许存在：

+贡献
-贡献

例如：

Germany   +3000
France    +2100
Spain     -1800
...
----------------
Total     +10000

这是非常重要的内部一致性校验。

如果：

sum(country_delta) != total_delta

则：

整个归因结果不得进入回答。

这比单纯测试几个数字更重要。

还要注意“贡献率”不要简单叫百分比

例如：

Total Δ = +1000
Germany Δ = +1500
Spain Δ = -500

那么：

Germany contribution = 150%
Spain contribution = -50%

数学上没有问题，但用户很容易误解成：

Germany 占全部销售额 150%。

所以建议 UI / API 明确区分：

delta_amount
contribution_share_of_change

而不要只叫：

percentage

并且允许：

>100%
<0%

这是正常现象。

# 企业销售分析 Agent · 项目复盘

> 这份文档回答四个问题：**强在哪、弱在哪、学到什么、接下来做什么**。
>
> ★ 缺点部分是**真的缺点**，不是「为了更好地进步」那种客套话。

## 一、这个项目解决的是什么问题

目标用户是不会也不想写 SQL、但每周必须出一份固定格式销售报表的人。痛点写得很具体：从 Excel 或数据库导数据、拉透视表、算指标、套格式，**每次 1-2 小时**，而且算错了很难发现。所以链路是「说一次，之后照着出」：一句话提需求 → AI 理解 → 出方案给人工确认 → 固化成任务（版本冻结）→ 之后自动取数、代码算数、在参考报表的副本上原地改样式、产出一份 Excel 加一段文字解读。

定位在评审后收窄过一次：从「AI 自动做销售报表」（这块已被 Ilka / ConnectReport 这类产品覆盖）改成「面向固定业务报表的**可确认、可复现、可审计**的自动化系统」。这个收窄决定了后面所有取舍——不追覆盖度，追数字能不能对得上。

## 二、强在哪（优点）

**1. 「数字一律由代码算」是硬约束，不是口号。** LLM 只做两件事：理解需求（→ Intent）与组织语言（→ 解读）。`app/engine/**` 里没有任何一行 import `app/ai`（实测零命中），反向的 `app/ai/tools.py` 明确依赖 engine，这条单向关系写成了 `app/ai/__init__.py` 里的硬约束。意义是「算数字」可以脱离 LLM 单独运行、单独测试，LLM 不可用时服务照常出报表。模型想报错数也过不去：`app/ai/answer.py` 的数字核对闸门要求 LLM 文字里的数字与工具算出的数字一致，对不上就拦。

**2. 口径先冻结，再写实现。** 评审阻塞项的原话是：口径不定死，executor 与测试 Oracle 会共用隐含假设，测试全绿也不代表口径正确。于是有了 `D16` 销售额口径清单：时间字段 `InvoiceDate`、区间含首尾全天、排除 `InvoiceNo` 以 `C` 开头的取消单、排除 `Quantity <= 0`、排除 `UnitPrice <= 0`、`CustomerID` 为空不排除但在 `validations` 里报告空值行数、重复行不去重只报告、金额公式 `sum(Quantity * UnitPrice)`。清单要求逐条以注释形式出现在 `app/engine/metrics.py` 里，可枚举、可核对。

**3. 测试 Oracle 刻意不复用被测代码。** `tests/test_executor.py` 里的 Oracle 自己重新 `read_excel` 一遍、自己算一遍，再跟引擎输出比对——同一个 bug 要同时出现在两条独立实现里才会漏网。配合数据快照 SHA256 核对（`loader.EXPECTED_SHA256`，`/api/health` 也会回带），「同一个输入必须得到同一组数字」才有可复核的基础。

**4. 「事实与推断分离」做成了答案的形状。** 资料 + 销售数据的联合分析输出三段，顺序与标题固定：`【一、已知事实 —— 来自你的资料】`、`【二、已知事实 —— 来自销售数据】`、`【三、分析与建议（我的推断，不是事实）】`。第三段是唯一可能由模型写的部分，要过既有数字闸门（合法数字集合 = 资料引用 + 数据事实 + 工具返回值），**出现一个追溯不到的数字或写错币种就整段作废**。实测机器逐段扫过：第三段的数字全部能在前两段找到。

**5. 检索不用向量库，但给出了可解释的替代。** `app/ai/doc_index.py` 用纯 Python 实现 BM25（k1=1.2 / b=0.75，标准值不调参——调参要标注集，本项目没有），中文按字符 2-gram、英文按整词，不引 jieba。命中要两道同时成立：覆盖率（中文 2-gram ≥ 0.4）+ 至少一个稀有词真的对上。位置回退的规矩是：正文里有 `## 第 N 页` 才写页码，没有写「第 N 节」，连标题都没有写「第 N 段」，**绝不按字数估页码**。零新依赖。

**6. 资料正文不进提示词——这是最关键的取舍。** 回答由**代码摘录原文**组成（命中引原句 + 出处；概览每节挑一句 + 出处），LLM 完全不参与。因为「每个事实点都能在原文找到」只有原句摘录能结构性保证；模型复述一遍要证明它没混进别的东西，就得再写一套句子级溯源闸门。这同时把提示词注入变成结构事实——实测同一句销售问题在导入带注入语句的资料前后，数字**逐位相同**。

**7. 冻结资产真的有守卫。** `test_业务表不碰冻结资产` 用 AST 逐块比对：metrics / executor / renderer 仍逐字节相同，loader 里 HEAD 已有的每个函数与顶层常量逐字节相同，**只有 `load_raw` 放行**。开缓存豁免时 diff 恒为 `+191 / -1`，唯一被删掉的那行就是原来的 `pd.read_excel(...)`。负向证明也跑过：在 `sha256_of_file` 里偷加一行 → 守卫立刻报错。

**8. 验证是「真跑一遍」。** 有真浏览器 CDP 走查（`fr003_import_cdp.mjs` 18/18、`fr010b_documents_cdp.mjs` 44/0、`fr010c_joint_cdp.mjs` 39/0），在页面上用 `getBoundingClientRect` 量几何而不是读代码；有真杀进程重启的 e2e（`stepc_accounts_e2e.py` 34/34 验证账号真的落盘）；**clean-room 验证**也在全新克隆、全新 venv、无解析缓存的目录里真跑过，`/api/health` 回带的 sha256 与原仓库一致。

## 三、弱在哪（缺点）

**1. 文档里定义的成功指标，一条都没测量过——这是最严重的问题。** `requirements.md` 写得很明确：数字准确率 ≥ 98%（人工核算 50 个数据点）、需求理解准确率 ≥ 85%、格式还原度 ≥ 90%、端到端成功率 ≥ 80%、失败归因分布、人工确认必要性边界场景 100%，还有一份 8:2 切分、固定随机种子的留出集。而 `TASKS.md` 显示 `TASK-006 Evaluation Harness`（`run_eval.py` + 样例集，5 项子指标）**从未开始**，`tests/test_cases.json` 那 50 条测试集一直只是清单。也就是：磁盘上有 1206 条通过的单测，产品对外承诺的六个指标是零测量。对一个主打「可复现、可审计」的系统来说，这比缺功能更严重。

**2. 单测全绿漏掉过真实回归，因为当时跳过了全量测试。** FR-012 为修「2011年11月的客单价」加了一条兜底，条件只写了「解析给 unsupported **且** 路由判它是单值直答」，**少了第三个条件——这个 unsupported 是谁给的**。于是「华南区上个月卖了多少？」也被救成 `sales_summary`，拿到一个**用 Country 顶替「华南」算出来的数字**，看着像答案、其实答的是另一个问题。7 条用例转红，而当时按用户要求跳过了全量测试，所以没被发现。更早还有 `TASK-001-FIX` 记下的遗留：`c03` / `e08` / `e09` / `e10` 的口径描述与已冻结的 `D16` 冲突，需要裁决，一直没裁。

**3. 状态文件丢过数据、而且只在单进程下安全。** README 写明：状态落盘是 JSON 文件 + 进程内锁，两个 worker 同时「读-改-写」`tasks.json` / `executions.json` 会互相覆盖，现场表现是「执行记录凭空少了几条」——最难查的那类问题。所以 `serve.py` 把 `workers=1` **写死在代码里**，直接用 uvicorn 命令就绕过了这道保护。`ARCHITECTURE.md` 也确认当前持久化是 `state/*.json`，**不是关系数据库**，`D8` 的 MySQL 落库被推迟到 TASK-007。

**4. 权限只做了身份，没做授权。** `ARCHITECTURE.md` 6.2 写得很直白：游客限制（导入 / 导出 / 改任务 / 账号管理 / 删除）主要写在 `web/session.js` 的 guard 里，表现是 ⚠ 记号 + 弹窗拦截 + 不发请求，**服务端只拦了账号管理那三条**（`api_auth.py` 里 3 处 `require_admin`）。业务端点（对话、数据集、业务表、文档、执行）不做登录校验，**前端 guard 是绕得过去的**。会话存在内存里的模块级 dict、无签名、无权限范围、重启即失效。「写到桌面」也只在服务端进程与用户桌面同机同会话时成立。

**5. 一堆「界面上写了但不存在」的功能。** `TASKS.md` 与 `ARCHITECTURE.md` 第 7 节列着：定时调度**未实现**（没有任何调度器，也没有 cron 配置）、关系数据库落库未实现、服务端 RBAC 未实现、登录失败次数限制与锁定未实现、多进程部署未支持、`/api/parse` 与 `/api/spec/{id}` 未实现。最后两个尤其尴尬——「大白话 → Spec」是核心卖点，而文档明说 Spec 目前由便捷路径或完整 Spec 直接提交，**不经过 LLM 解析**。

**6. 数据面的真实覆盖很小。** 只有一份 `data/Online Retail.xlsx`：541,909 行 × 8 列，覆盖 2010-12-01 ~ 2011-12-09（54 周），38 个国家 / 4,372 个客户。需求 MVP 里写着「MySQL 连接」，但真正验证过的路径是 Excel。这份数据加载一开始 `pd.read_excel` 实测 **101.95 秒**（早期注释里还有 250 秒的记录），服务端预热实测 **318.6 秒**，那段时间 GIL 被占满、别的请求全被饿着——CDP 走查时表现为「点了导入页面一直转、服务端日志里连那条 POST 都没有」。

**7. 有一条已知 flaky 测试没修，理由是「不在本次范围」。** 上传两份文档后列表倒序，「新的在前」这条断言约有一半概率翻车。取证跑了 20 遍：10 遍两份落在同一秒，其中 4 遍顺序翻车；没打平的 10 遍全部正确——打平与翻车一一对应。根因是 `now_iso()` 精度只到秒，同一秒内排序由随机 `doc_id` 决定。**没修**，因为改精度或排序键属于既有链路口径变更，如实记录留给单独一张单子。但它现在仍然在测试套件里随机红。

**8. 分层文档比代码旧，能力也有天花板。** `ARCHITECTURE.md` v2 标注「最后核对日期 2026-09-28，对应 commit `017fa8e`」，而 FR-010-B / C / 011 / 013 / 014 的改动全在它之后——文档自己写了「如与代码冲突，以代码和最新 DECISIONS 为准」。能力上：资料检索只做**字面匹配**（2-gram + BM25），问得越口语化越容易落进「没找到」，走向量库又撞上「不引重型依赖」的红线；回答是「原文 + 出处」的清单体，不如人写的摘要顺口；不做 OCR，图片型 PDF 在导入那一步就提不出文字；不做预测外推；地区维度没有多级下钻，导入没有流式进度。「11 月」不带年份会落到整个数据区间（Q-003）仍未做。

## 四、踩过的坑（学到什么）

**1. 让 LLM 算数的诱惑，用行业数据否掉。**
现象：text-to-SQL 类方案看起来很自然——模型读表、生成 SQL、算完返回。
根因：LLM 算数不可靠，Spider 2.0 显示真实企业 schema 上 text-to-SQL 准确率仅 **10.1%**。
教训：数字一律由 pandas 算，LLM 只负责「怎么问、怎么讲」；开源项目 `ad-report-builder` 同样选「0 LLM 介入算数」，属于行业验证过的选择（D4）。

**2. 测试全绿不等于口径正确。**
现象：executor 和测试 Oracle 都「通过」了，但两边共用同一个隐含假设——「上周」到底按哪个日期字段、含不含退货。
根因：这是评审点名的最大风险，**不是「AI 理解错」，而是「语义正确但计算口径错误」**。
教训：先冻结口径清单（D16）并让实现逐条对应，可枚举可核对；再让 Oracle 独立实现（D12）。

**3. 一份「看起来正常但数字错」的报表比没有报表更危险。**
现象：同一周数据实测有 382 行完全重复、重复行金额 1,298.10、占净额 0.421%，不去重算 316,412.16、去重后 315,114.06。
根因：原始数据可能有重复录入，去重与不去重是两个都说得通的口径。
教训：维持「不去重、只报告重复行数」并在报告里如实报出来——错误可见比被藏起来强。`D10` 定了同一条：任一步失败就记录错误 + 不出文件，不做降级输出（D17-3）。

**4. 任何问题都会被拖进销售流水线。**
现象：施工前原样问进去，「我放的周报在哪里」被当成销售分析算了 14 行表；「1+1等于多少？」算了 7 行表；「什么是毛利率？」直接 unsupported。
根因：不在模型，在链路——既有 8 个 intent 全是销售类，关键词闸门里 `多少` 这种高频词一出现就往销售上靠，渲染层又无条件先拼一段「算出来的事实」。
教训：加一层**纯代码的路由**当进门第一件事（`question → intent 分类 → intent 专属处理 → response_mode → 渲染`，禁止反向），分类顺序本身是规格，**分类失败默认澄清、绝不默认 sales_summary**；数学走受限 AST 计算器（白名单节点、自己递归、禁 `eval`/`exec`，`10**100000000` 在求值之前就被拒）（D24）。

**5. 一条偶发测试的背后是一个精度问题。**
现象：`/api/documents` 上传两份文档后列表顺序随机翻转，测试时好时坏。
根因：`now_iso()` 精度是**秒**，同一秒上传的两份文档时间戳打平，谁在前由随机 `doc_id` 决定。
教训：写取证脚本跑 20 遍，把「打平」与「翻车」的对应关系坐实，再用 `git diff` 证明它在本轮改动之前就存在——**不修测试、不许「顺手改绿」**，如实记录留给单独一张单子。

**6. 兜底盖住闸门，等于把用户的问题换成另一个问题。**
现象：修「客单价」时加的兜底，把「华南区上个月卖了多少？」也救成了 `sales_summary`，用户拿到一个用 `Country` 顶替「华南」算出来的数字。
根因：兜底条件少了「这个 unsupported 是谁给的」——`guard_unsupported` 是用代码硬拦「数据里没有这个维度」的，它产出的 unsupported 本来就不该被救。
教训：兜底加前提 `parse_info["source"] == "llm"`，**代码闸门永远压过兜底**。而且不再加一道恒真的重复判据——「两处各抄一份、迟早漂移」这个亏本项目已经吃过（D30）。

**7. 乱码的根因要钉到字节层，兜底要能被证明「不生效」。**
现象：一份 12 页 PPT 导出的 PDF，库里标题是 `'\x00A\x00I\x00 n8b\x0fR6O\wå\x8bÆ^\x93'`，3295 字符里有 **511 个 NUL**。
根因：字体是 `/Type0` + `/Encoding /UniGB-UTF16-H` 且**没有 ToUnicode 表**，pypdf 解码时把 2 字节 UTF-16 的字节对齐搞坏了，高位字节丢成 NUL；而 `_clean()` 只折叠空白、不清 NUL，坏数据一路进库再显示给用户。
教训：兜底只在**可疑页**上跑，且**两道闸门都过才替换**。「正常 PDF 不受影响」要有两条独立证明：正常 PDF 三条判据一条不中、兜底函数一次都不会被调用；就算误进兜底也换不掉原文，因为正常页脏字符数是 **0**，**不可能有谁严格少于 0**。实测正常 PDF 改前改后逐字节相同，坏 PDF 从 511 个 NUL 变成 0（D29）。

**8. 「dev 断言过了」不等于「代码能构建」。**
现象：`ProposalsPage.tsx` 里 `apiPatch` 未使用，CDP 断言全过，`npm run build` 才报错；删菜单项后 `SyncOutlined` 变成未使用导入，19 页断言全过，还是只有 build 报错。根因是 dev server 走 HMR、不做类型检查。
教训：必须同时跑 `tsc` + `npm run build` + CDP 断言，三件套不能省。更早的同类是 `tsc --noEmit` 在这套解决方案式 tsconfig 下**一直什么都没检查**——一个从不失败的检查等于没有检查，修完必须做反向测试证明它真的会失败（D47 ④ / D48 ⑤ / D53）。

**9. 断言跟着旧行为写，测试通过反而掩盖回归。**
现象：`ai-assistant-entry.txt` 原本写着「点击后落到工作台」，那是按旧行为写的，功能改了之后它仍然「通过」。根因是断言描述的是历史行为，不是当前应有的行为。
教训：**断言要跟着行为改**，否则绿灯会盖住回归。同类还有：把 `analytics.txt` 复用给风险中心页导致 13 项无意义失败；客户详情页的「访问事件」断言用了没有访问记录的客户——那是测试数据指错，不是页面坏了（D34 / D52 ④ / D58 ⑨）。

## 五、技术栈

| 层 | 用了什么 | 为什么 |
|---|---|---|
| 后端 | Python 3.11.x + FastAPI + uvicorn | 轻量、自动文档、与 pandas 生态无缝。**钉 3.11**：`pandas 3.x` 与 `openpyxl 3.1.5` 只在 3.11.15 上验证过 |
| 计算与渲染 | pandas；`engine/**` 冻结；openpyxl 原地改模板 | 数字的唯一来源；`engine` 不 import `ai`，可脱离 LLM 单独测。`pandas.to_excel` 会丢合并单元格 / 字体 / 列宽，而用户要「像这个」 |
| 存储 | `state/*.json` + 进程内锁；新导入落 SQLite | 单机单进程够用，抽象接口留着换实现。SQLite 只放行不放算：只允许 `SELECT payload`，SUM / GROUP BY 不许写进 SQL——换了存储不等于换了计算引擎 |
| 前端 | 原生 HTML / CSS / JS，分文件 | 页面少，不值得引 Vue/React；但也否掉 2MB 巨型单文件 |
| AI | 直接调 LLM API（OpenAI 兼容）+ 显式状态机 | 流程是固定几段（解析→确认→固化→执行），不是自主循环；LangChain / LangGraph 一律否掉 |
| 检索与文档解析 | 纯 Python BM25 + 中文 2-gram；`python-docx` / `pypdf` / `python-pptx` | 不引向量库 / embedding / RAG / jieba，命中原因要可解释、可回原文核对；不引 OCR / LibreOffice / Office COM |
| 测试与验证 | pytest（含独立 Oracle 对账）+ 真浏览器 CDP 走查 + e2e / smoke / 门禁脚本 | 产出是数字，需要独立实现对账；UI 与「真杀进程重启」必须在真实环境里量出来，clean-room 跑一遍才算基线 |

- 做 `TASK-007`：定时调度 + 执行记录绑定 spec / 数据 / 模板 / 代码版本 + 重启恢复 + 任务锁。
- 做 `TASK-006 Evaluation Harness`：把 `requirements.md` 里那六个指标真正测出来，含 8:2 留出集。指标可以先难看，但不能一直没有。

**中期**
- 把 `state/*.json` 换成真正的数据库，顺带解掉 `workers=1` 的死限制。
- 服务端业务级权限控制：现在前端 guard 绕得过去，这条不补，「多用户」就只是界面上的说法。
- 接上 `/api/parse` 与 `/api/spec/{id}`，让「大白话 → Spec」走真实的 LLM 解析，而不是靠人工构造 Spec 兑现。

**明确不做的**
- 预测 / 外推。联合分析只讲**已经发生**的事。
- 向量数据库、知识图谱、模型微调、复杂 RAG。理由不是「不会」，而是需求是结构化字段映射；现有 BM25 的每个命中原因都能回原文核对，换成相似度分数反而更难解释。
- OCR 与图片型 PDF。读不出的就如实说读不出，不拿推测的内容顶上。
- 在线编辑 Excel、BI 拖拽仪表盘、实时流处理、多租户：都在 `requirements.md` 的非目标清单里。

## 七、一句话总结

这个项目最有价值的地方，是用一份可核对的「冻结口径」把 LLM 挡在算数之外，并真把这条边界跑成了 1206 条测试和多次 clean-room 复现；最大的问题同样是诚实的——`requirements.md` 里那六个成功指标一条都还没测过，持久化与权限也仍然停在「单机自用」这个形态上。

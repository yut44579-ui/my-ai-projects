# AI供应链 · 项目复盘

> 这份文档回答四个问题：**强在哪、弱在哪、学到什么、接下来做什么**。
>
> ★ 缺点部分是**真的缺点**，不是「为了更好地进步」那种客套话。

## 一、这个项目解决的是什么问题

目标用户是做 B2B 供应链生意的小团队：客户资料散在几个 Excel 和几个人手里，发给老板的报表口径不一，老板问「这个月到底新进了几个真实客户」时没人能立刻给出可核对的答案。他们要的不是又一个仪表盘，而是「数字从哪来、这句话是谁说的」都能点开看的东西。

同时这个项目是我拿来验证一件事的：把 LLM 放进一个有真实业务数字的系统里，最大的风险不是它不够聪明，而是它编东西、以及它替公司对外做出没人授权的承诺。所以整条链路的第一目标不是「AI 好用」，而是「不许说假话」：业务数字三态可追溯，AI 的安全拦截写在代码层，未实现的能力如实置灰并写明原因。

## 二、强在哪（优点）

**1. 用数据契约把「编数字」这条路堵死。** 所有业务数字必须包成 `EvidenceValue = {value, state, source_type, evidence_ref}`，state 三态互斥：`VALID`（value 可以是 0）、`NO_DATA`（value=null）、`ERROR`。`0` 绝不允许用来表示「没有数据」，前端不得自己算业务数字（不许拿 `customers.length` 显示成「客户数」）。数据分析页据此把「算不了」和「算出来是 0」分开：分母为 0 或样本不足返回 null 显示「—」，分母非 0 且确实没人转化才返回 `0.0`。

**2. AI 安全拦截在代码层，不在提示词里。** `services/policy_gate.py` 的 `evaluate_policy` 是纯代码函数，判定词表写死在代码里，模型完全不参与「要不要转人工」的判断。覆盖报价、折扣、合同承诺、大额订单、付款、退款、银行账户、赔偿、法律承诺、重大投诉、特殊资源承诺、高价值客户关键承诺、异常资金 13 类敏感场景；命中就不调 LLM，直接落 `HUMAN_REQUIRED`。LLM 生成完的草稿**还要再过一次同一个闸门**，模型自己写出的「已经给你 8 折」一样拦下——宁可丢一条草稿，也不让承诺出街。

**3. 导入链路的可追溯性和脏数据处理是完整的。** 预览/提交是两步接口，commit 要带预览时那份文件的 sha256，不一致就 `400 sha256_mismatch`；同一份文件（sha256 相同）不允许重复导入，返回 `409 duplicate_import` 并告诉你是哪个 batch。编码按 UTF-8 BOM → UTF-8 → GB18030 的顺序探测，解不开就报 `parse_error`，**不乱码硬解**。CSV 走标准库 `csv`、XLSX 走 `openpyxl` 并统一 `str` 化，刻意不引 pandas——从根上杜绝「自动类型推断把电话读成科学计数、丢前导零」。计数有恒等式 `rows_total = rows_created + rows_deduplicated + rows_skipped` 由代码断言守住，破坏就报错。失败语义分两层：文件级失败零入库、不落批次行；行级失败整行跳过，原因只许用冻结枚举。

**4. 「空值绝不参与匹配」是真想清楚了才写的。** MySQL 里 `NULL = NULL` 结果是 NULL（不命中），但 Python 里 `None == None` 是 `True`——同一份去重逻辑在两边行为相反。实现上的防法是空值根本不构造查询条件，候选一律由 SQL 产生，Python 侧从不做 `None == None` 的比较。另外 email/phone 都空的两行不是当新客户，而是各自 `PENDING_REVIEW` 交人工，因为「压根没有可比的键」和「查不到」是两件事。

**5. 防幻觉做成了结构性约束，不靠提示词自律。** 获客研究强制把输出分成 `{"facts": [...], "inferences": [...]}` 两段，每条 fact 必须带 quote，服务端逐条回验 quote 是不是 `source_text` 的逐字子串（只归一化空白，不改任何字符），验不过的一律剔除并如实报告 `rejected_count`；inference 必须带 basis。知识库那边，知识在 `knowledge_documents/chunks`、业务数据在 `customers/opportunities`，不同表、不同 evidence_ref 前缀，`/knowledge/analyze` 分成 `knowledge_used` 与 `business_data` 两个独立字段返回。模型想混也混不了。

**6. 把「检查本身不可靠」当成一个要修的问题。** 面向用户的文案不许出现 markdown 记号，这条规则被违反过 4 次，于是做了 `scripts/check_user_text.py` 扫描器；第一版只扫 GET 漏掉 POST 响应，改；后来从「手写接口清单」改成从 `openapi.json` **自动发现接口**，覆盖从 23 个接口提升到 40 个，未覆盖的 51 个逐条列出原因（「缺样例 id」「无探针」「HTTP 422」）——关键不是数字变大，而是**漏掉的会被看见，而不是默默跳过**。前端构建那侧也补了 `npm run typecheck`（`tsc -b --force`）。移动端加了 `scripts/check_mobile.mjs`，用真移动端视口逐页量内容宽度与横向溢出，桌面断言全过发现不了的问题它能发现。

**7. 认证是「先定规格再实现」的。** 规格文档 `docs/AUTH_SPEC.md` 是首份：口令用标准库 PBKDF2-HMAC-SHA256（21 万次迭代、每用户独立 16 字节盐、`hmac.compare_digest` 恒定时间比较），会话用自签 HMAC 令牌，不引 JWT 库、不建 sessions 表。受保护范围用「默认全保护 + 显式放行」——逐条给路由加鉴权依赖的问题是漏加一条就是未鉴权后门且难发现，现在新增业务路由默认就是受保护的。无状态令牌的失效代价用 `users.token_version` 补，代价是校验时会查一次用户，这是刻意的取舍。

## 三、弱在哪（缺点）

**1. 没有真实数据，产品最核心的价值主张没有被验证过。** `docs/TODO_HANDOFF.md` 里写得很清楚：客户来源是「11 个客户没有一个真实来源」，全部来自测试样本导入。系统号称有 15 个汇报指标，但支持它们的业务数据是零。对做供应链数字产品的项目来说，这是最大的硬伤——所有「数字可追溯」的设计都只在几十行样本上跑通过。

**2. 系统实际可操作性和「已完成」的说法之间有明显落差。** 按决策记录：客户 AI 回复**没有接知识库**（D49 ⑥明确记为「本轮不修，属独立 TASK」），实测里用户问「机房温度有什么要求」，知识库里其实有「建议 22 度以下」，但模型只能如实说「这个我得确认一下」；营销与内容模块**没有任何发送能力**（D42 ④：`confirm` 只是标记这条话术可用，触达由人工自己做）；`AUTH_SECRET_KEY` 同时用于加密数据连接凭据，密钥泄露等于凭据泄露（D40 ④自己写明了这条边界）。

**3. 数据库内部不自洽。** TODO_HANDOFF 同时写着「数据库表 19 张」和「**17 张表**：…」并逐一列出 17 个表名，两份数字差 2 且文档没有解释。作为一份给面试官看的材料，这种对不上号本身就是一个失分点——而这个项目其它地方最强调的就是「口径必须唯一」。

**4. 单租户是锁死的，不是配置项。** D3 冻结「不做 tenants」，Repository 层只保留 scope 参数作为迁移口。一个真实公司要用它，第一个需求就是多部门或角色隔离，这个改动会动到几乎所有接口。同时 `users.token_version` 让每次鉴权多一次主键查询，三级以上权限矩阵明确不做。

**5. 定时与后台能力完全没有。** 项目**刻意不上 Celery/cron**（D58 ④自己写的），于是「实时在线状态」只能读时推算、不能落库：存下来的结果在两次扫描之间必然是旧的，而存储方案需要定时任务不停扫描。所有动作都要人手动点，没有任何自动执行。

**6. 导入不可撤销，是 V1 的硬边界。** `IMPORT_RULES.md` §8 明确：只做 CSV/XLSX，不接 PDF/Word/PPT/企业微信/邮件/CRM，不做客户编辑/删除/导出，**不做撤销导入**。演示时唯一的安全网是 `scripts/cleanup_test_data.*` 按文件 sha256 清测试数据——真实的误导入没有回退路径。

**7. 自动化检查长期不可靠，是踩了三次才补上的。** `tsc --noEmit` 在这个项目里**从来没有检查过任何文件**（解决方案式 tsconfig + `--noEmit` 不构建 references，永远 exit 0）；「dev 断言过但构建失败」发生过至少两次（`apiPatch` 未使用、`SyncOutlined` 未使用）；markdown 扫描器两次漏检（漏 POST、漏前端 JSX）。这类「看起来在跑、其实没有效力」的验证漏洞被发现时，代码往往已经这样活了几轮。

**8. 前端还有已知的重复实现，没统一。** `BrandLogo.tsx` 与 `public/favicon.svg` 是同一份图形的两份拷贝（HTML 与 TSX 是两套运行环境，无法互相引用），改图形时两处都要改——目前只在两处文件顶部互相标注。`REPORTS.md` 整篇停留在 TASK-007 时代（写「metric 白名单只有两个」，而后端已扩到 15 个并有前端页），是明显过时的文档。

## 四、踩过的坑（学到什么）

**1. 某个枚举加了成员，另一张表先炸了。**
现象：扩 `customers.lifecycle_status` 后，写新状态时 `customer_events` 插入报 `1265 Data truncated for column 'to_status'`。
根因：MySQL 的 ENUM 是**字面量列表**，且**类型名被多个列共用**——只改了「表名看起来对的那个」。
教训：扩 ENUM 前先查 `information_schema.COLUMNS WHERE COLUMN_TYPE LIKE '%<枚举值>%'`，把**所有**引用列一起改（`evidence_source_type` 被 5 张表共用，同理）（D36）。

**2. 类型不对，但名字很像。**
现象：`datetime.now(REPORT_TIMEZONE)` 抛 `TypeError: tzinfo argument must be None or of a tzinfo subclass`；另一处把指标的 `row_kind` 标成 `customer`，下钻去取 `obj.name` 报 AttributeError → 500。
根因：`REPORT_TIMEZONE` 是**字符串**（要写成快照里的自解释字段），而 `datetime.now()` 要 tzinfo 对象。
教训：**「名字像」不等于「类型对」**，跨模块传递前先确认类型；常量名带 TIMEZONE 不代表它是 tzinfo（D39）。

**3. 同名类的覆盖是静默的。**
现象：`/api/dashboard/summary` 直接 500，报 `Column expression ... expected, got <class 'app.schemas.dashboard.DataConnection'>`。
根因：同一模块先导入 Pydantic 版 `DataConnection`，后导入 ORM 版，后者把前者覆盖了，构造响应那行拿到的是错的对象。
教训：一个模块同时用 ORM 与 schema 时先看有没有同名；同名就给 ORM 侧一律加别名（本次改成 `DataConnectionRow`），别指望「用的时候记得区分」（D41）。

**4. 声称「可回溯」就必须让它可被断言验证。**
现象：知识库切片第一版把若干 `strip()` 过的段落**拼接**成切片内容，却用原始区间做偏移，结果 `text[char_start:char_end] != content`，实测 3/4 片偏移错误。
根因：拼接字符串 + 记原始区间，两套坐标系必然对不上。
教训：**先在原文里把要合并的区间算准，最后按区间取子串**，全程只操作区间、不拼接字符串。修后 343 字 → 4 片，偏移不精确片数 0。「只要对外声称可回溯/可定位，就必须让这个声称可被断言验证，否则它只是注释里的一句好话」（D43 ④）。

**5. 一个从不失败的检查等于没有检查。**
现象：`npx tsc --noEmit` 报 exit 0，而 `App.tsx` 里用了没 import 的组件。
根因：`tsconfig.json` 是解决方案式配置，自己不含文件，而 `tsc --noEmit` **不构建 references**（要 `-b` 才会），这条命令永远检查 0 个文件。
教训：做了**对照实验**证明修好——故意删掉 import，`tsc --noEmit` 仍 exit 0（证实漏洞），`npm run typecheck` 抓到 TS2304，还原后 exit 0。检查修完必须反向验证它真的会失败（D53）。

**6. 同一个东西维护两份名字表，迟早对不上。**
现象：首页「今日汇报」把指标显示成原始英文键（`risk_open` / `message_read`…），中文界面里混英文。
根因：`dashboard.py` 自己维护了一份 `REPORT_METRIC_LABELS`，只写了 2 条，其余 13 个 fallback 成原始 key。
教训：修法**不是补齐 15 条**，而是删掉这份重复表，改为从 `services.reports.METRICS` 读 label。同一病根还表现为：两套文档存储互不相通、两处各写一份能力清单（被断言抓到漂移）（D23 / D48）。

**7. 无状态令牌必须补失效入口。**
现象：令牌签出去之后，改密码、停用账号都挡不住它，只能等它过期。
根因：自签 HMAC 令牌不落库，服务端没有任何「这条还有效吗」的检查点。
教训：加 `users.token_version`，改密码 / 停用 / 踢下线时自增，令牌 payload 里的 `tv` 不符即拒。代价是校验时要查一次用户——**明确写进规格当作刻意取舍**，而不是假装自己还是纯无状态（D29 / D30）。

## 五、技术栈

| 层 | 用了什么 | 为什么 |
|---|---|---|
| 后端 | Python 3.11+ / FastAPI / Pydantic | 轻量、自动生成 `/api/docs`；Pydantic 直接承担 EvidenceValue 契约 |
| 数据访问 | SQLAlchemy 2.x + Alembic + PyMySQL | 迁移必须可回滚（23 个迁移全部可逆）；`alembic.ini` 里的 url 故意留空，由 `migrations/env.py` 注入，源码里没有任何口令默认值 |
| 数据库 | MySQL 8（独立库 `biz_assistant`） | 时间列用 `DATETIME(6)`：默认只到秒的话，「命中即刷新 last_seen_at」在同一秒内无法观测（D16） |
| 前端 | React + TypeScript + Vite + Ant Design + React Router | 状态只用本地 state + fetch，明确不引 Redux / Zustand / TanStack Query——页面复杂度用不上 |
| AI | 直接 `httpx` 调 DeepSeek，不引任何 LLM SDK | 少一层依赖多一层可控性；供应商按「协议」分派（OpenAI 兼容 / Anthropic / Gemini），加一家兼容的只要登记 |
| AI 安全 | 自研 `policy_gate.py` 纯代码闸门 | Prompt 只负责表达，不负责安全；命中不调 LLM |
| 文件解析 | `openpyxl` + 标准库 `csv` / `hashlib` | 刻意不引 pandas / chardet：pandas 的自动类型推断会把电话变科学计数 |
| 凭据加密 | 标准库 PBKDF2 派生 + HMAC-SHA256 + 认证标签 | 不引 `cryptography`；改一个字节或换密钥都会抛错。边界写清了：防「数据库被拖走后凭据直接可读」，不防「能读到 AUTH_SECRET_KEY 的人」 |
| 测试与部署 | pytest + 真浏览器 CDP 脚本；腾讯云 + nginx | 页面断言、截图、移动端视口测量都在真浏览器里做，不 mock；后端只监听 127.0.0.1:8100，外网只能经 nginx，AI 接口限流 12 次/分钟/IP（实测连打 20 次 → 5 次放过、15 次 429） |

## 六、后续会怎么做

**近期（有明确落点）**
- 把 `knowledge.search()` 接进客户对话回复链路。这是 D49 自己记下的缺口：产品资料明明在库里，客户问参数时 AI 只能说「我确认一下」。
- 把 README / REPORTS.md 这类停留在早期 TASK 的文档按当前实现重写。REPORTS.md 说「metric 白名单只有两个」，实际已 15 个——文档说小了，读的人会以为功能没做完。
- 补一份带真实数据语义的演示数据集（来源、渠道、阶段齐全），让「数字可追溯」在真实分布上被验证一次，而不是只在几十行样本上。

**中期（要动结构）**
- 定时执行与后台作业：现在所有动作靠人点，这一步需要先设计 worker 方案，而项目一直刻意不引 Celery。
- 统一 `BrandLogo.tsx` 与 `favicon.svg` 的两份拷贝，改成构建期生成单一来源。
- 补数据连接器：CRM / ERP / 企业微信 / 官网 / API / Webhook 目前只有配置框架，测试会如实返回失败与原因。

**明确不做的**
- 多租户（D3 冻结）、工作流引擎、向量库 / RAG、微服务、Kafka、Redis、Docker：当初就否掉了，现在也不打算加——真正的问题是数据量和验证深度，不是架构复杂度。
- 用 LLM 打分做风险推断（「87% 概率是骗子」这类）。等级由类别决定：资金类 HIGH、价格承诺类 ATTENTION，FACT 与 INFERENCE 必须分离。

## 七、一句话总结

这个项目真正花力气的地方不是让 AI 多能说，而是在每个它可能乱说的地方装上代码层闸门和可核对的证据锚点；踩的坑绝大多数属于「对不上号」和「检查没有效力」，所以后半程的主要工作是把人工纪律升级成会失败、也验证过会失败的自动化检查。

| # | 文档要求 | 实测现状 | 性质 |
|---|---|---|---|
| 1 | §二 数据来源 6 种：REAL / IMPORT / SYNC / WEB / TEST / DEMO | `EvidenceValue.source_type` 只有 IMPORT / MANUAL / SYSTEM | 规格不符 |
| 2 | §九 客户状态 8 种，含「已联系·未读」「已读·未回复」「暂时沉默」「明确拒绝」 | 7 种，缺这 4 个语义（且有文档未要求的 QUOTED） | 规格不符 |

## 2. 关键设计判断（为什么这样改）

### 2.1 客户来源：**新加维度**，不挤进 CustomerSourceType
`customers.source_type`（REAL/TEST/MANUAL）的现有语义是**这份数据可不可信**，
被导入流程、报告排除测试数据、前端黄色告警等多处依赖。

§九 的 10 种是**获客渠道**（官网自然访问/展会/转介绍…），是**另一个维度**。

★ 合并会破坏既有语义：一次 TEST 导入的客户，其"获客渠道"可能是"Excel导入"，
两个维度**同时存在且都有意义**。所以新增 `customers.acquisition_channel`，
`source_type` 保持不动。数据血缘（D1 复用策略）不被破坏。

### 2.2 已读状态：**按钉钉语义设计**（用户裁定）
用户要求"就和钉钉那种一样，显示就可以了"。钉钉的语义是：
**消息发出后有「已读/未读」标记，显示给对方看**。所以要区分两件事：
- 「已联系·未读」= 我们发了、对方还没看
- 「已读·未回复」= 对方看了、还没回

★ 站内没有真实客户渠道（D9 禁止伪造客户消息），所以：
**已读状态由真实渠道写入**（将来企业微信/官网埋点回传），V1 只把
**状态值与接口准备好**，绝不自己造"客户已读"。
状态本身可以配置/显示，但是没有数据源时不会有客户处于该状态 —— 这是如实行为。

配套设施（同批做，否则"已读"无处显示）：
- `customer_messages.read_at` + `read_source`：一条消息何时被读、从哪个渠道读的
- 记录 `read_at` 时**必须同时写一条 customer_events 事件**（可追溯，§十一）

### 2.3 消息三个追溯字段：默认值要"不撒谎"
新增三列都是**可空布尔**，不用 `default=False`：因为
"还没人工确认"与"确认了不需要人工"是两件事，
"没有触发业务事件"与"没记录过"也是两件事。**NULL = 未记录/不适用**。

### 2.4 枚举扩展必须手写迁移（D20 已记的坑）
MySQL ENUM 是字面量列表，Python 侧加成员**不会**改列定义，
Alembic autogenerate 也检测不到。四个枚举要各写一条 `ALTER TABLE MODIFY COLUMN`。
不迁移直接写入新值 → 报 1265 "Data truncated"。

### 2.5 QUOTED 保留
文档 §九 状态清单里没有「已报价」，但它是既有 enum 值且有真实数据依赖
（`opportunities` 的商机阶段与 KPI 口径都用它）。
**删除枚举值会破坏已有数据**，所以保留：文档是"至少支持"，不是"只能是这些"。

## 3. 最小改动清单

**新增**
- `customers.acquisition_channel`（VARCHAR 枚举，可空）
- `customer_messages.read_at` / `read_source`
- `customer_messages.human_confirmed` / `auto_sent` / `triggered_event_ref`

**扩展枚举**
- `SourceType` += `SYNC` / `WEB` / `DEMO`
- `LifecycleStatus` += `CONTACTED_UNREAD` / `READ_NO_REPLY` / `SILENT` / `REJECTED`
- 新 `AcquisitionChannel`（10 值）

**迁移**：4 条 ENUM 扩展 + 1 条加列（合并为一个 revision）

**接口**
- `POST /api/customers/{id}/messages/{mid}/read`：标记已读（供真实渠道回传）
- 状态变更接口沿用（新状态自动可用）
- 列表接口支持按新状态/渠道筛选

**前端**
- 客户列表/详情显示获客渠道
- 消息时间线显示已读标记（钉钉样式：已读/未读）
- 新增状态的中文标签

## 4. 风险

| 风险 | 处置 |
|---|---|
| 枚举扩展导致既有数据被截断 | 迁移**只加值不删值**；downgrade 前先清理新值行（同 D20 写法） |
| 新状态让 analytics 漏斗 rank 失真 | 漏斗只对主线状态算 rank；新状态中"暂时沉默/明确拒绝"是**旁支**，不进主线 |
| 已读接口被滥用造"假已读" | 接口**要求传 source**（哪个渠道回传的），没有来源的已读请求直接 400 |
| 前端把"未记录"显示成"未确认" | NULL 与 False 分开渲染：NULL → 「—」，False → 「否」 |

## 5. 验收断言

```
① 枚举：SourceType 能取到 6 种；LifecycleStatus 能取到 11 种；AcquisitionChannel 10 种
② 写入：新状态/新渠道能真实落库并读回（不是只改枚举）
③ 已读：POST read 带 source → 200 且 read_at 非空、同时产生一条 customer_events
         POST read 不带 source → 400（拒绝无来源的已读）
④ 消息字段：三个可空布尔默认 NULL，能分别写 True/False 并读回
⑤ 迁移可逆：upgrade → downgrade → upgrade 往返成功
⑥ 回归：既有 11 个页面断言 + 后端 51 条路由全部仍通过
```

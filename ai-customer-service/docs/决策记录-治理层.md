# 里程碑 4：配置与信任层（急停 / 影子模式 / 后果预览）

> 这三样不是锦上添花，是**客户敢不敢开自动的决定因素**。
> 没有它们，客户只敢一直用"全部转人工" —— 那这套系统就等于没上。

客户的真实心理：
```
"万一它说错话了怎么办？"   → 需要**急停开关**（出事时那个能按的按钮）
"我怎么知道它答得对不对？" → 需要**影子模式**（先只算不发，拿数据说话）
"调了会怎样？"             → 需要**后果预览**（调旋钮时看到数据）
```

---

## D30 急停放在流程最前面，后面一步都不走

**决策**：`answer_question()` 第一件事就是查急停；生效时直接返回转人工，
**连检索和模型都不调**。

**理由**：
- 客户按这个按钮时的心态是"我要接管了"。这时候还去查资料、还去调模型，
  就是在浪费时间和钱做一件不会被采纳的事
- 而且"完全没参与"这个事实本身要如实告诉用户（reason 里写"AI 未参与"）

**★ 连草稿都不给**：有人会想"急停只停自动发，草稿还能帮人"。但那不对 ——
按了按钮还得逐条看草稿，按钮就没起到"停"的作用。

---

## D31 ★★ 急停必须留痕

**决策**：每次按/松都记 `谁、什么时候、为什么`。

**理由**：急停是"出事时"才会按的按钮。事后复盘时，
**"谁在什么时候按的、当时以为什么"是唯一能还原现场的东西。**
没有它，一次事故会变成互相猜。

**实现**：`stop_log` 表 + `/api/gov/stop/history`。
界面上直接显示最近几条。

---

## D32 ★★ 影子模式必须在**每一个出口**都生效

**现象**（重构的直接原因）：
影子开关最初写在函数末尾。但转人工的路径（意图命中、检索不到、
出站检查拦下）在函数**中间就 `return` 了** ——
于是影子期间"AI 答不上来"的那些**还是会真的转人工**，影响了真实流程。

**这是定义上的错误**：影子模式的意思是"完全观察、不影响任何东西"。
只覆盖一个出口，那就不叫影子模式。

**修法**：引入 `_finish()` 作为**唯一的收尾出口**，所有 return 都走它。
影子模式在这一层统一生效。

**★ 这条的普遍意义**：
> 凡是"全局生效"的开关（急停、影子、调试模式、限流），
> **都必须收敛到单一出口**。散落在多个 return 上，必然漏掉几个，
> 而漏掉的那几个恰恰是最危险的路径（异常路径）。

---

## D33 ★ `would_be_decision` 必须落库，不能靠重推

**现象**：影子报告最初是拿 `quality` 反推"本来会不会自动发"。

**问题**：重推会**漏掉意图命中（报价/投诉）和出站检查拦下的那些**，
把"本来会直接发"算多 —— 而客户正是拿这个数决定要不要开自动的。
算高了就是误导。

**修法**：新增 `qa_log.would_be_decision` 列，在收尾时落库。

**★ 教训**：
> 凡是**给客户看、用来做决策**的数字，都不能"事后推算"，
> 必须是**当场记录的原始判定**。重推和实际的差异，恰恰出在异常路径上。

---

## D34 ★ `intent` 也必须落库（后果预览靠它）

**现象**：后果预览报 `no such column: intent`。

**问题**：预览要复现"意图优先于分数"的判定顺序，
但配额里没存这个信息 → 只能按纯分数重算 →
会把"报价"这类**算成自动发**。

**这是最坏的一类 bug**：预览显示"开激进档能自动覆盖 85%"，
客户信了，结果报价问题全被自动发出去了。

**修法**：新增 `qa_log.intent` 列。

**★ 教训**：
> **预览必须和线上走同一套判定顺序。**
> 不一致的话，预览出来的数字就是骗人的 ——
> 而"后果预览"存在的全部意义就是让客户相信那些数字。

---

## D35 ★★ 后果预览不调模型 —— 所以它是免费的

**决策**：`preview()` 拿历史 `quality` 分按新门槛重放一遍，**不调任何模型**。

**理由**：每次问答的检索质量分**已经存在 `qa_log` 里了**。
重放只是把历史分数重新分一次类。

**实测**：20 次预览平均 **7.8 ms**。

**★ 这条的意义远超"省点钱"**：
```
因为免费，所以可以做到"拖滑块实时看数字"
因为免费，所以客户可以随便试，试到他敢
```
如果每调一次门槛要花几十次模型调用，这个功能在交互上就不成立 ——
它会变成"点一下等 30 秒"，没人愿意用。

---

## D36 档位必须真的能区分，否则预览是个摆设

**现象**：测试里三档算出的结果**完全一样**（保守/标准/激进都是 自动 5）。

**原因**：测试数据的质量分都是 0.9，三档门槛（0.86 / 0.72 / 0.58）都判 auto。

**这不是 bug，但说明测试没验到东西。** 补了中等质量（0.65 / 0.62 / 0.50 / 0.34）
的样本之后：
```
保守 自动5 起草2 转人工9
标准 自动5 起草3 转人工8
激进 自动7 起草2 转人工7
```
并加了单调性断言：自动发送量随档位放宽**单调不减**，转人工**单调不增**。

**★ 教训**：
> 测试数据全落在同一个区间时，断言会"全部通过"但**什么都没验证**。
> 要专门构造**落在边界附近**的数据，才能验到判定逻辑。

---

## D37 档位改之前先给后果，不直接生效

**决策**：界面上点档位 → 先显示后果对比 → 再让客户点"就用这个档位"。

**理由**：看不到后果，客户既不敢调，也不敢不调。
```
"自动发送覆盖率 65% → 58%，每天转人工从 23 条涨到 41 条 ——
 你只有 2 个客服，够吗？"
```
有了这句话，他才知道该往哪调。

**警告阈值**：转人工量增加 30% 以上就提示 —— 因为那通常意味着**要多招人**，
是老板才会拍板的事，不该悄悄发生。

## 这一轮又验证了一次的老问题

**现象**：从 PowerShell 调接口测中文，结果全是 0 命中、质量 0.0，
看起来像"检索坏了"。

**实际**：PowerShell 的 `ConvertTo-Json` 把中文请求体搞乱了。

**★ 这个坑在本项目里已经踩过三次了**（另两个项目里也踩过）。
所以现在的纪律是：**测中文接口一律用 Python 发请求，不用 PowerShell。**

★ 这一轮的急停留痕也栽在这上面：界面上显示成 `???`。
**界面没错，是我发坏的数据** —— 但这说明界面上应该有个"数据看着不对"的直觉，
不然很容易误判成功能坏了。

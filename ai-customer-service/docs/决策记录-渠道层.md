# 里程碑 3：渠道接入层（飞书 / 企微 / 模拟）+ 人工工作台

> 这一层的难点**几乎全在接入协议上，跟业务无关**，而且每一条都会真出事故。

---

## D38 ★★ 转人工时给客服的必须是「查到了什么」，不是 AI 那句话

**现象**（截图里发现的）：
工作台上 AI 的"草稿"显示成 `这个我答不了，我让人来回你。` ——
客服看了**等于什么都没看到**，还得自己从头查一遍。

**原因**：转人工时 `ans.text` 就是那句套话。
代码一股脑把它当"参考"塞进了人工队列。

**修法**：按转人工的类型分别处理：
```
draft    → AI 真的写了一句（只是没把握）→ 把那句给他，他改一改就能发
escalate → AI 写的是"我答不了"套话 → 给他**检索到的原文**，让他扫一眼就知道怎么说
```

**★ 而且 escalate 的那种**：
- 明确标注「AI 没有作答，以下是它查到的原文」——
  不标的话客服会以为这是 AI 的答案，直接复制发给客户
- **不预填进输入框** —— 预填了客服很可能看都不看就发出去，
  而原文里可能带内部措辞（比如"财务部应于…"）

**这条的普遍意义**：
> 给人工的"AI 输出"必须是**他真正需要的那个东西**，
> 而不是程序的内部中间产物。写代码的人知道那是套话，
> 但界面上看起来就是个正常的回答。

## D39 ★★ worker 的错误处理路径必须比主路径更健壮

**现象**（测试发现的）：
统计显示 `failed: 1`，但 `dispatch_error` 表**是空的**，
而且后续消息有的没被处理。

**原因**：第一版把"处理消息"和"记错误"写在同一个 try 里：
```
处理炸了 → 进 except → 记错误时又炸 → 异常冒到 _loop 外面
→ **worker 线程静默退出** → 后面所有消息都不处理，且没有任何提示
```

**修法**：`_record_failure()` 自己**绝不能抛异常**，
三段（改状态、写库、写内存）各自兜住。
另外在内存里也留一份错误，万一连写库都失败还能在界面上看到。

**★ 教训**：
> **错误处理路径必须比主路径更健壮。**
> 主路径出错是"这次没成功"，错误处理出错是"以后永远不成功且无人知晓"。

## D40 ★★ 「队列空」和「处理完」是两件事

**现象**（测试发现的）：一堆莫名其妙的失败 ——
人工队列是空的、入站状态还是 `accepted`、`processed: 0`。

**原因**：`drain()` 只等"队列为空"，但消息**从队列取出来之后还在处理中**
（生成答案、写库）。等队列空 = 在处理的窗口里读数据。

**修法**：加一个 `_BUSY` 标志，`drain()` 要等 **队列空 且 不在处理中**，
再额外等一拍避开边界。

**★ 教训**：
> 凡是"等某件事做完"的辅助函数，都要问清楚**做完的定义是什么**。
> "取走了"和"做完了"之间有窗口，而这个窗口恰恰是最容易读错数据的时刻。

## D41 去重必须落库，不能放内存

**决策**：`inbound_log` 表存 `message_id` 的去重记录，窗口 24 小时。

**理由**：
- 企微超时会**重发同一条消息**。去重记录放内存的话，重启后历史重试
  会被当成新消息 → 用户被答两遍，而且两遍可能不一样
- 这张表本身也是排查"为什么重复回复"的唯一依据

## D42 平台适配器只做翻译，不做判断

**决策**：`Channel` 接口只有三个方法：`verify` / `parse` / `send`。

**理由**：如果允许在适配器里写"这句话该不该转人工"，
那每家平台都要实现一遍，必然对不上（另两个项目都踩过 D46/D48 那个坑）。
**所有判断都在 pipeline 里，所有平台共享同一套。**

---

## D43 内部/外部判定必须保守

**决策**：飞书和企微都要配"内部员工名单"；
**名单没配时，一律当外部客户**。

**理由**：猜错的方向性完全不同：
```
猜成外部客户 → 少给信息（客户再问一次就好）
猜成内部员工 → 把报价底线、内部制度答出去（事故）
```
★ 所以默认值必须偏保守的那一边。

## D44 企微 AES 的两个易错点（写错了平台不告诉你哪里错）

```
① PKCS7 的块大小是 **32**，不是 AES 标准的 16。
   写 16 的话，明文长度刚好是 16 的倍数时不会填充，企微侧解密报错。

② EncodingAESKey（43 位）要**先补一个 '=' 再 base64 解码**，
   不是直接解 43 位。
```

**明文结构是三段，少一段都解不对**：
```
random(16) + msg_len(4, 网络字节序) + msg + receiveid
```
其中 `receiveid` 是**用来校验这条消息是不是发给自己的** ——
不校验的话，别人企业的密文也能解开（如果密钥泄露）。

**测试覆盖**：往返测试覆盖了 1 / 16 / 31 / 32 / 33 / 100 字，
其中 32 和 48 是块边界 —— **最容易出错的地方。**

## D45 飞书的长连接是中小企业私有化部署的唯一出路

**背景**：企微回调**必须公网 HTTPS**（不能用 IP:端口，不能自签证书）。
很多中小企业的服务器在内网，根本没有公网地址 ——
这一条直接卡死了他们。

**飞书支持长连接（WebSocket）接收事件**：
不需要公网域名、不需要证书、不需要配 IP 白名单。

**★ 所以产品化时的建议是**：
```
能选飞书就选飞书（免公网）
客户必须用企微 → 要么给他配个公网入口，要么用内网穿透（要跟他说清风险）
```

**本文件实现了事件订阅（Webhook）方式**，长连接需要 `lark-oapi` SDK，
没装就如实降级（不假装能用）。

## D46 协议实现没有真实凭据验证过 —— 必须如实标注

**决策**：飞书和企微适配器的注释里都明确写了
「按公开协议实现，**没有用真实企业账号验证过**」，并提供 `selftest()`。

**理由**：
- 平台文档会变，字段名会变，签名算法也可能调整
- **"看起来对"和"真的能通"是两件事**
- 不如实标注的话，接不上时第一反应是怀疑自己的配置，
  而不是怀疑这段代码

**已经能离线测到的部分（都测了）**：
```
✅ 签名算法（正确/错误/缺字段/重放）
✅ 内部外部判定（含"名单没配时保守处理"）
✅ 事件解析（URL 校验 / 文本 / 非文本 / 无关事件 / 坏报文）
✅ 企微 AES 往返（含 32 字节块边界、receiveid 校验）
✅ 企微 XML 解析
```

**必须在真实环境才能测的**：
```
⬜ 真的能收到平台推来的事件
⬜ 真的能把消息发出去
⬜ access_token 能正常拿到（缓存逻辑对不对）
```

## 这一轮实现的渠道能力

```
app/channels/base.py      契约（只做翻译，不做判断）
app/channels/dispatch.py  去重 + 异步 + 路由（★ 平台无关的共享核心）
app/channels/sim.py       模拟渠道（离线测 + 演示，不用注册企业号）
app/channels/feishu.py    飞书（验签 + 事件解析 + 发送 + token 缓存）
app/channels/wecom.py     企微（AES 加解密 + SHA1 验签 + XML 解析 + 发送）
web/workbench.html        人工工作台
```

**API**：
```
POST /api/channels/{platform}/webhook   平台回调入口
GET  /api/channels/wecom/webhook        企微 URL 校验
GET  /api/channels/stats                调度统计 + 最近入站
GET  /api/handover                      人工队列（带 AI 查到的东西）
POST /api/handover/{id}/take            接管（AI 随即停手）
POST /api/handover/{id}/reply           客服发出（改动喂给学习闭环）
POST /api/handover/{id}/reject          负反馈
```
